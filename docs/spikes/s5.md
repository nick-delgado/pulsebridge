# Spike S5: HL7v2 store notifications, HTTPS ingest and where to record the mapping outcome

## Answers

1. **Does ingest notify? Yes.** With `notificationConfigs` set on the HL7v2 store, both
   `messages:ingest` and `messages.create` publish one Pub/Sub message per newly stored HL7v2
   message. Rejected messages publish nothing.
2. **What the notification contains.** Very little: `data` is the stored message's full resource
   name (a path, not the HL7v2 content), and there is exactly one attribute, `msgType` (MSH-9.1,
   for example `ORU`; an empty string if MSH-9 is empty). The mapper must call `messages.get` to
   read the message.
3. **Duplicates.** Ingesting identical bytes again returns `AA` and the same message name, and
   publishes **no** second notification. The mapper must still be idempotent, because Pub/Sub
   itself may deliver any message more than once.
4. **Raw or `parsedData`? Parse the raw `data` with `hl7apy`.** `parsedData` is complete for our
   fields but its key format changes with the content (`"3.1"` becomes `"3[0].1"` when a field
   repeats), MSH is numbered one lower than HL7, and it cannot be produced without GCP. Details
   in "Stored message shape".
5. **Where to record the outcome: labels on the stored message.** `messages.patch` with
   `updateMask=labels` works, does **not** publish a notification (no loop), merges with existing
   labels, and `messages.list` can filter on them, including "has no outcome yet".
6. **HTTPS ingest** returns the same ACK and NACK content as MLLP: HTTP 200 with `hl7Ack` on
   accept, HTTP 400 with the NACK inside `error.details[0].hl7Nack` on reject. One difference in
   what counts as valid is in the comparison table.
7. **Two things the design had not accounted for.** The store does not keep the commit-level ACK
   or any rejected message, so the trace panel and messages log cannot get those from the store
   (see T14). And the topic-level IAM binding could not be shown to be *necessary* in this
   project, because the service agent already holds a project-level role that allows publishing.

Terms used in this note:

- **Pub/Sub** is Google's messaging service. A **topic** is a named channel that publishers send
  messages to. A **subscription** is a named queue attached to a topic; each subscription gets
  its own copy of every message.
- **Pull** means the consumer asks the subscription for messages. **Push** means Pub/Sub sends
  each message as an HTTPS POST to a URL (for us, the `v2-to-fhir` Cloud Run service). To
  **acknowledge** a message is to tell Pub/Sub it has been handled; an unacknowledged message is
  delivered again.
- A **notification** here is the Pub/Sub message the HL7v2 store publishes when it stores an
  HL7v2 message. It is unrelated to the HL7v2 ACK.
- A **service agent** is a Google-managed service account that a Google service uses to act
  inside your project. The Cloud Healthcare one publishes the notifications.
- **Labels** are small key/value strings attached to a cloud resource, here to one stored message.
- ACK, NACK, `AA`, `AE`, MSA-1/2/3 and MLLP are defined in `docs/spikes/s4.md`.

## Findings

### 1. Notifications

Ingest request and response (valid ORU^R01):

```
POST .../hl7V2Stores/main/messages:ingest
{"message": {"data": "<base64 of the ER7 bytes>"}}

HTTP 200
{
  "hl7Ack": "<base64>",
  "message": {
    "name": "projects/<project-id>/locations/us-central1/datasets/spike_s5/hl7V2Stores/main/messages/icMZ5BDXaSAnVHGIYad3MwJzgPIOM6nP856SvHBpAVY=",
    "data": "<base64, the bytes that were sent>",
    "sendFacility": "PULSEBRIDGE",
    "sendTime": "2026-11-13T22:46:06Z",
    "messageType": "ORU",
    "createTime": "2026-11-13T22:46:07.413166Z",
    "patientIds": [{"value": "SYN-000123", "type": "MR"}]
  }
}
```

`hl7Ack` decoded (segments separated by `\r`; no MLLP framing bytes and no trailing `\r`):

```
MSH|^~\&|PHR|PULSEBRIDGE|CUFFSIM|PULSEBRIDGE|20261113224607||ACK|2478b790-9ee0-4adf-b7de-a897e8fecc6b|P|2.5.1\rMSA|AA|S5-0001
```

The Pub/Sub message pulled from `spike-s5-pull`, complete:

```json
{
  "data": "<base64 of the string below>",
  "attributes": { "msgType": "ORU" },
  "messageId": "22613209518828696",
  "publishTime": "2026-11-13T22:46:08.131Z"
}
```

`data` decoded:

```
projects/<project-id>/locations/us-central1/datasets/spike_s5/hl7V2Stores/main/messages/icMZ5BDXaSAnVHGIYad3MwJzgPIOM6nP856SvHBpAVY=
```

- `msgType` is the only attribute. There is no control ID, patient, facility or event type.
- `msgType` was `ORU`, `ADT`, `ACK`, and `""` (present but empty) for a message with empty MSH-9.
- `messages.create` (`POST .../messages` with `{"message": {"data": ...}}`) published an identical
  notification. Its response is the `Message` resource directly, with no `hl7Ack`.
- No `orderingKey` was present.
- The message ID after `/messages/` is the URL-safe base64 of the SHA-256 of the message bytes
  (checked on one message). It can contain `-`, `_` and ends in `=`.

**Filters.** `notificationConfigs[].filter` works. The field is `message_type`, not `msgType` or
`type`. A store with three configs was sent three messages:

| Config filter | ORU from `PULSEBRIDGE` | ADT from `OTHERFAC` | ORU with empty MSH-9 |
| --- | --- | --- | --- |
| `message_type = "ORU"` | notified | no | no |
| `send_facility = "OTHERFAC" OR labels.route = "x"` | no | notified | no |
| (no filter) | notified | notified | notified, `msgType: ""` |

A message created with label `route=x` was notified on all three. One store can therefore fan
out to several topics.

Syntax accepted at store creation: `message_type = "ORU"`, `NOT message_type = "ADT"`,
`message_type != "ADT"`, `-message_type = "ADT"`, `send_facility = "X"`, `labels.route = "x"`,
`labels."route" = "x"`, `PatientId("SYN-000123", "MR")`, `send_date >= "2026-11-01"`,
`create_time > "2026-11-13T00:00:00Z"`, combined with `AND` / `OR`. Single quotes and unquoted
values were also accepted. The camelCase names `messageType` and `sendFacility` were accepted too
(their behaviour was not tested). Rejected with HTTP 400 `invalid filter "..."`:
`msgType = "ORU"`, `type = "ORU"`, `foo = "x"`, `type == ORU`, `message_type : "OR"`, a trailing
`AND`. Only the `message_type =`, `send_facility =`, `labels.x =` and `OR` forms had their
*behaviour* checked; the rest were only checked for being accepted.

### 2. Duplicates

The same bytes ingested three times into the default store:

| Attempt | HTTP | ACK | `message.name` / `createTime` | Notifications |
| --- | --- | --- | --- | --- |
| 1 | 200 | `MSA\|AA\|S5-DUP-1` | new | 1 |
| 2 | 200 | `MSA\|AA\|S5-DUP-1` (new ACK control ID) | same as attempt 1 | 0 |
| 3 | 200 | `MSA\|AA\|S5-DUP-1` | same as attempt 1 | 0 |

`messages.create` of an existing message behaved the same way: HTTP 200, same resource, no
notification. Labels already on the message survived a duplicate ingest.

With `rejectDuplicateMessage: true` the second ingest returned HTTP **409** `ALREADY_EXISTS`
with a NACK `MSA|AE|S5-RD|message already exists`, and no notification.

So the store deduplicates on exact bytes. Two messages that differ in any byte (for example
MSH-7) are two messages and two notifications, even with the same control ID.

### 3. IAM

The binding that was added, as read back from the topic:

```yaml
bindings:
- members:
  - serviceAccount:service-<project-number>@gcp-sa-healthcare.iam.gserviceaccount.com
  role: roles/pubsub.publisher
```

It applied without error; the service agent already existed.

**It was not shown to be necessary here.** A second topic with no topic-level binding
(`spike-s5-nobind`) also received its notification. The project's IAM policy (read only, not
changed) already grants the same service agent `roles/healthcare.serviceAgent` at project level,
which Google adds when the API is enabled, and that evidently allows publishing. The spike was
not allowed to remove that grant, so the topic binding could not be tested on its own.

Creating a store whose config names a topic that does not exist was refused, and no store was
created:

```
HTTP 403 PERMISSION_DENIED
Permission pubsub.topics.publish denied on resource projects/<project-id>/topics/spike-s5-does-not-exist (or it may be malformed or not exist)
```

So the publish permission is checked when the store is created or its config set. Whose
permission is checked (the caller's or the service agent's) is not known.

### 4. Direct HTTPS ingest

`POST .../messages:ingest` with `{"message": {"data": "<base64>"}}`.

Accepted, HTTP 200, body `{"hl7Ack": "<base64>", "message": {...}}` as shown above. `message`
holds `name`, `data`, `createTime` and whichever of `sendFacility`, `sendTime`, `messageType`,
`patientIds` could be read; never `parsedData`.

Rejected, HTTP 400. The NACK is inside the error details, and `error.message` repeats MSA-3
without HL7 escaping:

```json
{
  "error": {
    "code": 400,
    "message": "Invalid MSH header",
    "status": "INVALID_ARGUMENT",
    "details": [{
      "@type": "type.googleapis.com/google.cloud.healthcare.v1.hl7v2.IngestMessageErrorDetail",
      "hl7Nack": "<base64>"
    }]
  }
}
```

`hl7Nack` decoded:

```
MSH|^~\&|||||20261113225233||ACK|cf6fbef5-243b-4873-bdb2-dc5bcca37253\rMSA|AE||Invalid MSH header
```

Errors with **no** `hl7Nack`, which are API errors and not HL7 replies:

| Request | Result |
| --- | --- |
| Body `{}` | 400 `message data needed when ingesting hl7v2 message` |
| `data` not valid base64 | 400 `Invalid value at 'message.data' (TYPE_BYTES), Base64 decoding failed ...` with a `BadRequest` detail |
| Store does not exist | 404 `HL7 store: ... not found` |

`messages:ingest` also accepts `labels` in the request `message` (`{"transport": "https"}` was
stored).

### Comparison: HTTPS ingest (this spike) and MLLP (S4)

| Class | Message | MLLP, from S4 | HTTPS ingest | Stored / notified |
| --- | --- | --- | --- | --- |
| valid | ORU^R01, two OBX | `MSA\|AA\|<id>` | 200, `hl7Ack` = `MSA\|AA\|<id>` | yes / yes |
| odd, parseable | OBX-14 empty | AA | 200, AA | yes / yes |
| odd, parseable | OBX-5 `HIGH` with type `NM` | AA | 200, AA | yes / yes |
| odd, parseable | unknown code `99999-9` | AA | 200, AA | yes / yes |
| odd, parseable | MSH segment only | AA | 200, AA | yes / yes |
| odd, parseable | MSH-9 empty | AA | 200, AA | yes / yes, `msgType: ""` |
| barely HL7 | `MSH\|^~\&` followed by `\r` | `MSA\|AA` (S4 row b4) | 200, `MSA\|AA` | yes / not checked |
| barely HL7 | `MSH\|^~\&` with **no** `\r` | not separately tested | **400**, `MSA\|AE\|\|invalid segment terminator, store expects: "\E\r"` | no / no |
| unparseable | line feeds between segments | `MSA\|AE\|\|invalid segment terminator, ...` | 400, same NACK | no / no |
| unparseable | `\r\n` between segments | not tested | 400, `Invalid segment name "\nPI"` | no / no |
| unparseable | starts with PID, no MSH | `MSA\|AE\|\|Invalid MSH header` | 400, same NACK | no / no |
| unparseable | free text | `MSA\|AE\|\|Invalid MSH header` | 400, same NACK | no / no |
| unparseable | the three characters `MSH` | `MSA\|AE\|\|Invalid MSH header` | 400, same NACK | no / no |
| unparseable | MSH-1 says `\|`, fields use `#` | `MSA\|AE\|\|Invalid segment name "PID"` | 400, same NACK | no / no |
| unparseable | empty payload | `MSA\|AE\|\|request missing message.data` | 400, same NACK | no / no |
| duplicate | same bytes, default store | AA, stored once | 200, AA, same name | once / once |
| duplicate | same bytes, `rejectDuplicateMessage` | `MSA\|AE\|<id>\|message already exists` | **409**, same NACK | once / once |
| transport failure | store missing | adapter closes the connection, no ACK | 404, no `hl7Nack` | no / no |
| transport failure | bad MLLP framing | no reply, timeout | does not apply | no / no |

The ACK and NACK content is the same on both transports. Differences: over HTTPS the reply is
base64 in JSON with no framing bytes; a NACK arrives as an HTTP error, not a 200; and API failures
are an HTTP status with a JSON error, where MLLP gives silence. A valid message without a
trailing `\r` after its last segment was accepted (200, AA); the lone-header case shows the store
needs at least one `\r` in the message.

### 5. Stored message shape

`GET .../messages/<id>?view=<view>` on one message:

| View | Fields returned |
| --- | --- |
| `BASIC` | `name` only |
| `RAW_ONLY` | `name`, `data`, `sendFacility`, `sendTime`, `messageType`, `createTime`, `patientIds`, `labels` |
| `PARSED_ONLY` | as `RAW_ONLY` without `data`, plus `parsedData` |
| `FULL` and no `view` on get | all of the above |
| `SCHEMATIZED_ONLY` | metadata only (no schema is configured) |

- `messages.list` defaults to `BASIC`: names only. Pass `view=RAW_ONLY` or `FULL` to get more.
- `labels` is absent when there are none, and is never in `BASIC`.
- `data` is byte-for-byte what was sent.
- `sendTime` is MSH-7; with no UTC offset in MSH-7 it is read as UTC. `createTime` is the
  store's clock. `sendFacility` is MSH-4. `messageType` is MSH-9.1 only (`ORU`, not `ORU^R01`).
- `patientIds` is every repetition of PID-3: `value` from PID-3.1, `type` from PID-3.5.
- Fields the store could not read are simply missing (a lone `MSH|^~\&` has only `name`, `data`,
  `createTime`).

Trimmed `parsedData` for a made-up message containing a repeated identifier, a second coding in
OBX-3, a time zone offset and HL7 escape sequences:

```json
{ "segments": [
  { "segmentId": "MSH",
    "fields": { "0": "MSH", "1": "^~\\&", "3": "PULSEBRIDGE", "6": "20261113230500",
                "8.1": "ORU", "8.2": "R01", "8.3": "ORU_R01", "9": "S5-TRICKY-1", "11": "2.5.1" } },
  { "segmentId": "PID",
    "fields": { "0": "PID", "1": "1",
                "3[0].1": "SYN-000123", "3[0].4": "PULSEBRIDGE", "3[0].5": "MR",
                "3[1].1": "SYN-000999", "3[1].4.1": "OTHERSYS", "3[1].4.2": "1.2.3", "3[1].5": "PI",
                "5[0].1": "O\\T\\TEST", "5[0].2": "SYNTHIA" } },
  { "segmentId": "OBX", "setId": "0",
    "fields": { "0": "OBX", "1": "1", "2": "NM",
                "3.1": "8480-6", "3.2": "Systolic blood pressure", "3.3": "LN",
                "3.4": "SYS", "3.5": "Local systolic", "3.6": "L",
                "5": "120",
                "6.1": "mm[Hg]", "6.2": "mm[Hg]", "6.3": "UCUM",
                "7": "90-120", "11": "F", "14": "20261113230500-0500" } },
  { "segmentId": "OBX", "setId": "2",
    "fields": { "0": "OBX", "1": "3", "2": "ST", "3.1": "8478-0",
                "5[0]": "a\\F\\b \\S\\ c", "5[1]": "second rep" } }
] }
```

What the key format means:

- Keys are strings: `field`, `field.component`, `field.component.subcomponent`. A field with no
  components has a bare key (`"5"`), one with components has no bare key (`"3.1"`, never `"3"`).
- **A repeated field changes the key for every repetition**: `"3[0].1"`, `"3[1].1"`. The same
  PID-3 with a single identifier is `"3.1"`. A reader must try both forms.
- **MSH is numbered one lower than HL7**: MSH-9 is `"8.1"`, MSH-10 is `"9"`, MSH-12 is `"11"`.
  Other segments match HL7 numbering (OBX-3.1 is `"3.1"`).
- Empty fields have no key. Key order is arbitrary.
- `setId` on OBX is the store's own zero-based counter, not OBX-1.
- Escape sequences (`\T\`, `\F\`, `\.br\`) are **not** decoded. `hl7apy` does not decode them
  either, so neither input saves that work.

`hl7apy` 1.3.5 on the same raw bytes (`parse_message(raw, find_groups=False,
validation_level=TOLERANT)`) returned MSH-10, both PID-3 repetitions with their components,
OBX-3.1/3.3, OBX-5 (as a list of repetitions), OBX-6.1 and OBX-14 using HL7's own names
(`msg.msh.msh_10`, `obx.obx_3.obx_3_1`). It also parsed the barely-HL7 messages the store
accepts (MSH only, lone `MSH|^~\&`, empty MSH-9). It **raised `UnsupportedVersion`** for MSH-12
`9.9`, which the store accepts.

**Recommendation: the mapper's input is the raw `data`, parsed with `hl7apy`.** Fetch with
`view=RAW_ONLY`.

| Concern | `parsedData` | Raw `data` + `hl7apy` |
| --- | --- | --- |
| Completeness for OBX-3/5/6/14, PID-3, MSH-10 | Complete | Complete |
| Field addressing | String keys, MSH shifted by one, key shape depends on repetitions | HL7 names; repetitions are lists |
| Escape sequences | Not decoded | Not decoded |
| Schema dependence | Depends on the store's `parserConfig` (version, custom schema), which is fixed at store creation | Depends only on the pinned library version |
| Testing without GCP | Fixtures must be captured from a real store | The T07 sample messages are the fixtures |
| Showcase value | Hides the parsing in a Google-specific JSON shape | Reads as HL7; the same library builds and validates in T07 and T13 |
| Tolerance | Whatever the store accepted is present | Raises on an unknown MSH-12; the mapper must catch this and record an `error` outcome |

The store's metadata fields (`messageType`, `patientIds`, `sendTime`) are still useful to T14 for
the messages log, where no parsing is wanted.

### 6. Recording the outcome in labels

```
PATCH .../messages/<id>?updateMask=labels
{"labels": {"application_outcome": "error", "reason": "missing-obx-14"}}

HTTP 200
{ "name": "...", "sendFacility": "PULSEBRIDGE", "sendTime": "...", "messageType": "ORU",
  "createTime": "...", "patientIds": [...],
  "labels": {"application_outcome": "error", "reason": "missing-obx-14"} }
```

- **No notification was published** after this patch or after about 30 further label patches
  (subscription polled for 5 to 10 seconds each time). Patching labels cannot loop.
- **Patch merges.** A second patch with `{"mapped_at": "..."}` left the first two labels in
  place. Patching the same key overwrites it. Setting a key to `null` or `""` removes that key
  only. `{"labels": {}}` changes nothing.
- `updateMask` is required (`400 must specify a field_mask`) and only `labels` is allowed
  (`400 invalid field mask, only labels can be updated`). Message content is immutable.
- A message that does not exist gives `404 resource not found`.
- **Constraints.** The API documentation gives the usual limits: at most 64 labels; keys 1 to 63
  bytes, starting with a lowercase letter, then lowercase letters, digits, `_` or `-`; values up
  to 63 bytes of the same characters. **None of these were enforced**: uppercase keys and values,
  spaces, `/`, `:`, a 64-character key, a 2,000-character value, a key starting with a digit and
  65 labels were all accepted and read back unchanged. Treat the documented limits as the
  contract anyway; unenforced behaviour can change.
- **`messages.list` filters on labels**, and a patched label was visible to the filter at once:

| Filter | Result |
| --- | --- |
| `labels.application_outcome = "error"` | the one message labelled `error` |
| `labels.reason = "missing-obx-14"` | the same message |
| `message_type = "ORU" AND labels.application_outcome = "error"` | the same message |
| `labels.application_outcome = "error" OR labels.application_outcome = "accepted"` | both labelled messages |
| `NOT labels.application_outcome:*` (also `-labels...:*`) | the 11 messages with no outcome label |
| `labels.application_outcome != "error"` | 12: every message without that value, including unlabelled ones |
| `send_time >= "2026-11-13T23:10:00Z"` | the three messages with that MSH-7 |

- `orderBy=send_time desc` works. `orderBy=create_time` is refused (`invalid order by key`).
  `send_time` is the sender's MSH-7, and messages without one sort first in ascending order.

**Is there a better place?** Not for this project. Alternatives considered:

| Place | Why not |
| --- | --- |
| FHIR `Provenance` or `OperationOutcome` in the FHIR store | An `error` outcome has no Observation to attach to; it would put non-clinical bookkeeping in the clinical store |
| A database (Firestore, Cloud SQL) | A new component and a new API to enable for two strings per message |
| An `ACK` message written into the HL7v2 store (D7's optional idea) | Works (below), but the log would have to join each message to its ACK by MSA-2; labels are on the message itself and filterable |
| Logs only | Not queryable by the proxy without a logging dependency |

Labels keep the outcome on the thing it describes, need no new service, and list-filter directly.

### 7. Writing an ACK back into the store

`messages.create` of this message into the three-topic store:

```
MSH|^~\&|PHR|PULSEBRIDGE|CUFFSIM|PULSEBRIDGE|20261113231500||ACK^R01^ACK|S5-APPACK-1|P|2.5.1
MSA|AE|S5-A1|missing OBX-14
```

HTTP 200, stored with `messageType: "ACK"`. It **did publish a notification** on the unfiltered
topic (`msgType: "ACK"`) and did not on the `message_type = "ORU"` topic. So if D7's optional ACK
is ever built, the mapper would be triggered by its own ACK unless the topic is filtered or the
handler drops `msgType == "ACK"` first.

```json
    "publish_time": "2026-11-13T22:46:08.131Z"
  },
  "subscription": "projects/<project-id>/subscriptions/<subscription-name>"

```

Also documented and not observed: a `deliveryAttempt` number is added when the subscription has a
dead-letter topic; with OIDC authentication enabled the request carries
`Authorization: Bearer <JWT signed by Google>` for the configured service account; any of HTTP
102, 200, 201, 202 or 204 acknowledges the message and anything else causes a retry.

## Design consequences

### T05, healthcare module

- Use the store's notification config list (in the Google provider, the `notification_configs`
  block with `pubsub_topic` and optional `filter`; confirm the block name against the pinned
  provider version).
- Declare the topic-level binding explicitly: `roles/pubsub.publisher` on the ingest topic for
  `service-<project-number>@gcp-sa-healthcare.iam.gserviceaccount.com`, with the project number
  from a data source. It was redundant in this project but makes the module independent of the
  project-level default grant. Make the store depend on the topic and the binding, because store
  creation fails with 403 if it cannot publish.
- **No filter on the notification config.** D7 wants messages with an empty or wrong MSH-9 to
  reach the mapper and end as application-level `error`; a `message_type = "ORU"` filter would
  leave them with no outcome at all.
- Keep `rejectDuplicateMessage` at its default: a resend is then a harmless `AA` with no second
  notification.
- The dead-letter topic also needs its own subscription, or dead-lettered messages are lost.

### T12, v2-to-fhir

- Handler steps: decode `message.data` to the message name; if `attributes.msgType` is `ACK`,
  acknowledge and stop; `GET <name>?view=RAW_ONLY`; base64-decode `data`; parse with `hl7apy`;
  map; write to FHIR; `PATCH <name>?updateMask=labels`; return 204.
- Input is the raw ER7 (recommendation above). State that in the service README.
- Catch every `hl7apy` exception, including `UnsupportedVersion`, and turn it into an `error`
  outcome with a reason. A 404 on `messages.get` (message deleted) should also be acknowledged.
- Idempotency is still required. The store will not re-notify for identical bytes, but Pub/Sub
  is at-least-once, and a resend with a new MSH-7 is a new message with the same control ID. The
  conditional update keyed on MSH-10 covers both.
- Labels: `application_outcome` = `accepted` or `error`; `reason` = a short lowercase code such as
  `missing-obx-14`, `non-numeric-obx-5`, `unknown-obx-3-code`, `unsupported-message-type`,
  `unparseable-by-mapper`. Stay inside the documented label limits (lowercase letters, digits,
  `_`, `-`, 63 bytes) even though they were not enforced. Human-readable text for each code lives
  in the dashboard, not in the label.
- Patch only the keys you own; patch merges, so other labels (for example `transport`) survive.
  On reprocessing, overwrite both keys in one patch so a stale `reason` cannot remain.
- The service account needs to read and update messages in the HL7v2 store. The predefined role
  for that was not tested here; confirm on first apply.
- Skip the optional ACK write. Labels carry the same information, and the ACK would re-trigger
  the mapper.
- The `Provenance` target is the message name from the notification; it is stable for given bytes.

### T13, cuff simulator HTTPS transport

- Present both transports as one result shape: `{acknowledged: true, code, control_id, reason,
  raw_ack}` or `{acknowledged: false, why}`.

| HTTPS result | Same as MLLP result | Shown as |
| --- | --- | --- |
| 200 with `hl7Ack` | ACK frame with `AA` | Commit-level `AA` |
| 400 or 409 with `error.details[].hl7Nack` | ACK frame with `AE` | Commit-level `AE`, reason from MSA-3 |
| Any error without `hl7Nack` (400 bad request, 403, 404, 5xx), or a network error | Connection closed or timeout | "No acknowledgment received", with the HTTP status and `error.message` |

- Decode `hl7Ack` / `hl7Nack` from base64 and parse with the same T07 ACK parser. The bytes have
  no MLLP frame and no trailing `\r`; the parser must not require one.
- Do not treat HTTP 400 as a transport failure before looking for `hl7Nack`.
- The "send malformed" samples behave the same on both transports (no MSH, line-feed
  terminators). There is no HTTPS equivalent of the bad-framing sample; over HTTPS, offer only
  the samples that apply.
- The ingest response's `message.name` is worth returning to the caller: the dashboard can use it
  to find the message and its outcome later.
- Optionally send `labels: {"transport": "https"}` with the ingest so the log can show the
  transport. The MLLP adapter cannot set labels, so absence would mean MLLP.

### T14, messages log and trace lookups

- List with `GET .../messages?view=RAW_ONLY&orderBy=send_time desc&pageSize=N`; filter with
  `labels.application_outcome = "error"`. Messages not yet processed are
  `NOT labels.application_outcome:*`; show them as "pending".
- `sendTime` is the sender's clock from MSH-7. There is no ordering by `createTime`.
- **The store keeps neither the commit-level ACK nor rejected messages.** `hl7Ack` exists only in
  the ingest response (or on the MLLP socket). So:
  - For stored messages the commit-level acknowledgment is `AA` by definition; the log can state
    that, but cannot show the original ACK bytes unless something saved them.
  - `AE` and no-acknowledgment attempts appear nowhere in the store. If the messages log should
    list them, the simulator must record its own send attempts (in its response to the dashboard
    for the current session, or somewhere durable). This needs a decision.

### D7

- The outcome mechanism is confirmed: labels `application_outcome` and `reason` on the stored
  message, written by `messages.patch`, with no risk of a notification loop.
- A third visible state exists: stored with `AA` but no outcome label yet (mapper not run,
  failed, or dead-lettered). Call it "pending" in the log.
- The optional ACK write is possible but causes a notification; recommend dropping it.

### Proposed brief and workplan edits (for the orchestrator)

- Brief, "Open questions and spikes": tick "HL7v2 store notification" with: `ingest` and `create`
  both publish; the Pub/Sub message carries only the message name and a `msgType` attribute;
  duplicates do not re-notify; push body not observed.
- Brief, data flow 2: "Ingest publishes the stored message's name to Pub/Sub; `v2-to-fhir`
  fetches the message, parses the raw bytes with `hl7apy` ...".
- Workplan D7 bullets: replace "Optional: `v2-to-fhir` also writes an `ACK^R01`..." with a note
  that it is not built because labels cover it and an ACK would re-trigger the mapper; add the
  "pending" state.
- Workplan T05: add an AC for the topic-level publisher binding and "no notification filter".
- Workplan T12: fix the input choice to raw ER7; change "suggested: labels" to "labels"; add an AC
  that a notification with `msgType` `ACK` is acknowledged and ignored, and that an `hl7apy`
  exception becomes an `error` outcome.
- Workplan T13: add the HTTPS result mapping above (400/409 with `hl7Nack` is a NACK, not an
  error).
- Workplan T14: add the open point on where the commit-level ACK and rejected attempts come from.

## What was not verified

- **Push delivery.** No endpoint; the push body, OIDC token, retry and dead-letter behaviour are
  from documentation only.
- **Whether the topic-level binding is needed.** The service agent already had project-level
  `roles/healthcare.serviceAgent`, and a topic without the binding still received notifications.
  Whose permission the store-creation check tests is also unknown.
- **Least-privilege roles** for the mapper (read plus label update on messages) and for the
  simulator's HTTPS ingest. Every call here used one broadly privileged service account.
- **Pub/Sub redelivery.** Every pulled message was acknowledged at once; a redelivered
  notification was not observed.
- **Notification failure.** What the store does if publishing fails after the message is stored
  (for example the topic is deleted later) was not tested.
- **Filter behaviour** beyond `message_type =`, `send_facility =`, `labels.x =` and `OR`. The
  other forms were only checked for being accepted. `NOT message_type = "ACK"` against a message
  with an empty type was not tried.
- **Label limits.** Only that the documented limits are not enforced today; the true upper
  bounds were not found.
- **`messages.list` at scale**: paging and consistency were seen only with about 20 messages.
- **Bare `MSH|^~\&` over MLLP without a trailing `\r`.** S4's row b4 does not say whether its
  payload ended in `\r`; over HTTPS the difference decides between `AA` and `AE`.
- **`parserConfig` versions V2/V3 and custom schemas**, and `SCHEMATIZED_ONLY` with a schema.
- **Terraform.** Nothing was applied with Terraform; the provider block name is from memory.
- **The message-ID-is-SHA-256 observation** was checked on one message only.
- **Latency through the MLLP adapter to notification**, and Cloud Run cold start.
