# Spike S3: Google Health API registration and one day of heart rate

## Answer

It works. With an OAuth client created by hand and one read-only scope, we authorised the author's
account, stored a refresh token in Secret Manager, and pulled one day of Pixel Watch heart rate.
Three findings change the design:

- **Data points have no `name`.** The brief keys idempotent writes on the Google data-point
  `name`. Every heart-rate point came back without one. The idempotency key has to be built from
  the patient and the sample time instead.
- **The volume is about 37,000 points a day,** one every 1 to 3 seconds, not one every 5 seconds.
  Storing each as a FHIR Observation means over a million resources a month. The API has a
  roll-up method that returns one minimum, average and maximum per time window; one-minute windows
  give about 1,440 values a day.
- **In Testing status the refresh token expires after 7 days.** The public demo needs the OAuth
  app moved to "In production", or the deployer must reconnect weekly.

No heart-rate values, timestamps, tokens or client secrets appear in this note. Examples below use
made-up values.

## What was tested

- Date: 2026-11-13. API: Google Health API `v4`, base URL `https://health.googleapis.com/`.
- Source of the API facts: the API's public discovery document
  (`https://health.googleapis.com/$discovery/rest?version=v4`) and live calls. Google's developer
  site could not be reached from the test environment, so nothing here is taken from the official
  guides.
- OAuth app: consent screen with user type External, publishing status Testing, the author as a
  test user. OAuth client created in the console.
- Scope requested: `https://www.googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly`.
- Device: one Pixel Watch 4.

## Terms used

- **OAuth client**: the identity of our application at Google, made of a client ID (public) and a
  client secret (private).
- **Scope**: a named permission the user grants, here "see health metrics and measurements".
- **Authorization code flow**: the user approves in a browser, Google sends the browser back to a
  redirect address with a one-time code, and the application exchanges that code for tokens.
- **Access token**: a short-lived credential sent with each API call.
- **Refresh token**: a long-lived credential used to get new access tokens without the user.
- **PKCE**: an extra check on the code exchange (a random verifier and its hash) that stops a
  stolen code being used by someone else.

## Findings

### 1. Registration and consent

Steps the deployer does by hand in the Google Cloud console:

1. Enable the Google Health API.
2. Configure the OAuth consent screen: External, Testing, add yourself as a test user.
3. On the Data Access page, add the scope above.
4. Create an OAuth 2.0 client ID.
5. Put the client ID and client secret into Secret Manager.

There is no heart-rate-specific scope. The API has about twenty scopes, grouped by category
(activity and fitness, health metrics and measurements, sleep, nutrition, and so on), each in a
read-only and a write-only form.

### 2. The connect flow

The flow planned for T11 worked end to end:

1. Read the client ID from Secret Manager and build the consent link with
   `access_type=offline`, `prompt=consent`, a `state` value and a PKCE challenge.
2. The user opens the link, approves, and the browser is sent to
   `http://127.0.0.1:<port>/?state=...&code=...`.
3. Exchange the code at `https://oauth2.googleapis.com/token` with the client ID, client secret,
   redirect address and PKCE verifier.
4. Store the refresh token as a new Secret Manager version.

Token response fields: `access_token`, `expires_in` (3599 seconds), `refresh_token`,
`refresh_token_expires_in` (604799 seconds, which is 7 days), `scope`, `token_type`.

In this spike the redirect address was pasted by hand because the script ran on a remote machine.
A script running on the deployer's own computer can listen on that port and skip the paste.

### 3. Which scope covers heart rate

`googlehealth.health_metrics_and_measurements.readonly` alone was enough for both calls below.
The discovery document lists the same long set of scopes on the list method for every data type,
so it does not say which scope maps to which data type; this was found by trying.

### 4. Identity

`GET v4/users/me/identity` returned `200` with three fields: `name`, `healthUserId` and
`legacyUserId` (the old Fitbit user ID). `healthUserId` is a stable identifier for the person and
is a candidate for the FHIR `Patient.identifier`.

### 5. Listing heart-rate points

Request:

```
GET https://health.googleapis.com/v4/users/me/dataTypes/heart-rate/dataPoints
    ?filter=heart_rate.sample_time.physical_time >= "2026-01-01T00:00:00Z"
            AND heart_rate.sample_time.physical_time < "2026-01-02T00:00:00Z"
    &pageSize=10000
Authorization: Bearer <access-token>
```

- The data type in the path is `heart-rate` (kebab-case); in the filter it is `heart_rate`
  (snake_case).
- The filter takes `>=` and `<` on the sample time, joined by `AND`.
- Response top level: `dataPoints` and, when there is more, `nextPageToken`.
- **Page size:** we asked for 10,000 and received 5,000 per page. The default is 1,440.
- **Volume:** 37,219 points for 24 hours, in 8 pages, fetched in 6.9 seconds.
- **Spacing:** median 2 seconds, minimum 1, maximum 3. No two points shared a timestamp.
- **Order:** newest first.

One data point, with made-up values:

```json
{
  "dataSource": {
    "recordingMethod": "PASSIVELY_MEASURED",
    "platform": "FITBIT",
    "device": { "displayName": "Pixel Watch 4" }
  },
  "heartRate": {
    "sampleTime": {
      "physicalTime": "2026-01-01T14:05:09Z",
      "utcOffset": "-18000s",
      "civilTime": {
        "date": { "year": 2026, "month": 1, "day": 1 },
        "time": { "hours": 9, "minutes": 5, "seconds": 9 }
      }
    },
    "beatsPerMinute": "72"
  }
}
```

Field notes:

| Field | Finding |
| --- | --- |
| `name` | Absent on all 37,219 points. The discovery document says it is "only supported for the subset of identifiable data types". |
| `heartRate.beatsPerMinute` | A JSON **string**, not a number. Documented range 1 to 300. |
| `heartRate.sampleTime.physicalTime` | UTC, whole seconds, format `YYYY-MM-DDTHH:MM:SSZ`. |
| `heartRate.sampleTime.utcOffset` | The user's offset from UTC as seconds with an `s` suffix, for example `-18000s`. |
| `heartRate.sampleTime.civilTime` | Local date and time as separate numbers. A part that is zero is omitted (no `hours` at midnight, no `minutes` on the hour). |
| `heartRate.metadata` | Absent. The schema allows `sensorLocation` and `motionContext`, but the watch did not send them. |
| `dataSource.device` | Only `displayName`. The schema also allows `manufacturer` and `formFactor`; neither was present. |
| `dataSource.platform` | `FITBIT` for every point. |
| `dataSource.recordingMethod` | `PASSIVELY_MEASURED` for every point. |
| `dataSource.application` | Absent. |

### 6. Roll-up

`POST v4/users/me/dataTypes/heart-rate/dataPoints:rollUp` with a time range and a window size
returns one value per window:

```json
{
  "startTime": "2026-01-01T14:05:00Z",
  "endTime": "2026-01-01T14:06:00Z",
  "heartRate": { "beatsPerMinuteMin": 70, "beatsPerMinuteAvg": 72.4, "beatsPerMinuteMax": 75 }
}
```

- With 60-second windows over 24 hours: 1,419 windows in one page, in 0.9 seconds. Windows with no
  data are left out.
- Here the minimum and maximum are JSON numbers and the average is a decimal number, unlike the
  string in the raw points.
- The maximum range for a heart-rate roll-up is 14 days per request.
- The discovery document says roll-ups exclude points recorded while the watch was not worn.

### 7. Webhooks

Not tested; nothing was created. From the discovery document:

- A project registers a **subscriber** with an HTTPS endpoint, which Google verifies when it is
  created. Each notification carries an `Authorization` header with a secret we choose, and a
  signature in a `GOOGLE-HEALTH-API-SIGNATURE` header.
- A **subscription** ties one user and a list of data types to a subscriber.
- The discovery document does not describe the notification body, so whether it carries samples
  or only says "new data is available" is still unknown.

## Design consequences

### Idempotency key (brief, T06, T10)

The brief says conditional updates are "keyed on the Google data-point `name`". There is no name.
Use a key built from stable parts, for example the patient identifier, the LOINC code and the
sample time (or the window start time for a roll-up). No two points shared a timestamp in the
sample, so the sample time is unique per patient for one device.

### How much to store (needs a decision)

| Option | Observations per day | Notes |
| --- | --- | --- |
| Every sample | about 37,000 | Over a million a month. Cost and chart performance both suffer; a 30-day chart cannot draw a million points. |
| One-minute roll-up | about 1,440 | One Observation per minute holding the average, with minimum and maximum as components. One API call per day of data. |
| Fifteen-minute roll-up | about 96 | Cheapest, but a coarse chart for the 24-hour view. |
| One Observation per window holding the raw samples as FHIR `SampledData` | about 96 to 1,440 | The FHIR-standard shape for a waveform, but it assumes evenly spaced samples and these are 1 to 3 seconds apart. |

Recommendation: one-minute roll-ups. They match the API's own default page size of 1,440, keep the
FHIR store small, and the minimum, average and maximum map cleanly onto one Observation.

### `health-sync` (T10)

- Use `rollUp`, not `list`, if roll-ups are chosen. Request at most 14 days per call; the backfill
  command must split longer ranges.
- If raw points are ever listed: expect 5,000 per page and follow `nextPageToken`.
- Parse `beatsPerMinute` from a string. Do not assume `civilTime` parts are present.
- Use `physicalTime` for `effectiveDateTime` and apply `utcOffset` so the FHIR time carries the
  user's local offset.
- Results arrive newest first.
- A sync every 15 minutes should re-request a window that overlaps the previous one; the
  idempotency key makes the overlap harmless. A roll-up window that was only partly synced will
  change on the next run, so the write must be an update, not create-if-absent.

### FHIR mapping (T06)

- `Device`: only a display name is available ("Pixel Watch 4"). There is no serial number or
  manufacturer, so the Device identifier has to be derived (for example from the patient and the
  display name).
- `Patient.identifier`: `healthUserId` from the identity call is available.
- `Provenance`: `dataSource.platform` and `dataSource.recordingMethod` are available to record
  where the reading came from.
- The trace panel's "Google Health JSON it came from" tab shows a roll-up window, not a single
  sample, if roll-ups are chosen.

### Connect script (T11) and secrets

- Three secrets, as decided: client ID, client secret, refresh token. The flow above is the script.
- Use PKCE and a `state` value. Request `access_type=offline` and `prompt=consent`, or Google
  returns no refresh token.
- The script should report when the refresh token will expire (`refresh_token_expires_in`).
- `health-sync` must handle an expired or revoked refresh token with a clear "reconnect needed"
  status in the dashboard's status strip, not a crash.

### OAuth app status (setup guide, T28)

- Testing status: only listed test users can connect, and refresh tokens last 7 days.
- For a long-running demo the app has to be "In production". Whether Google then requires
  verification for these health scopes was not tested.

### Proposed brief edits

- Data flow step 1: replace "conditional updates keyed on the Google data-point `name`" with a key
  built from patient, code and time; state the chosen granularity.
- Decisions log, wearable source: "about 5 s heart-rate samples" becomes "samples every 1 to 3
  seconds, about 37,000 a day".
- Open questions: tick "Google Health API registration", noting that the webhook payload is still
  unknown.

## Not verified

- The webhook notification body, and whether webhooks are worth using over the 15-minute poll.
- Moving the OAuth app to "In production", and whether verification is required.
- How soon after a measurement a point becomes available through the API (sync delay from watch
  to phone to cloud).
- Whether roll-up windows are aligned to the requested start time or to the clock.
- Other data types, more than one device, and time zone changes within a day.
- API quotas and rate limits.
- The official guides, which could not be reached.

## Cleanup and what remains

- The raw heart-rate response was deleted. Only structure, counts and timing were recorded.
- A third secret holding the refresh token now exists in Secret Manager next to the two the
  deployer created. It is meant to stay; it expires in 7 days while the app is in Testing status.
- No subscribers, subscriptions or other resources were created.
