# Spike S6: reviewer login (Identity Platform, a password in the proxy, or something else)

Desk research, 2026-11-13. No code was written and nothing in GCP was touched.

## Recommendation

**Use option B: one shared password, stored in Secret Manager, checked by `fhir-proxy`, which
hands the browser a signed token that expires after 8 hours. Do not use Identity Platform.**

Three reasons decide it:

1. **A shared credential is not an identity, so an identity service adds parts without adding
   security.** Identity Platform would hold exactly one account whose password is given to
   everyone. The security property is the same as option B (whoever knows the secret gets in).
   What it adds is a Firebase SDK in the page, a public API key, a user that Terraform cannot
   create, and a second place where the credential lives.
2. **It is the only option that Terraform creates and destroys completely.** The Identity
   Platform configuration cannot be deleted: the provider's delete step only forgets it. That
   conflicts with the brief's "`terraform destroy` leaves nothing behind" and with the nightly
   destroy test. Option B is one secret and one IAM binding.
3. **It matches the brief's wording as written.** "Credential in Secret Manager, rotated" is
   literally what option B is. A stranger's quick-start needs no console step and no extra API.

Runner-up: option A (Identity Platform). It loses on reasons 1 and 2, not on cost (it is free at
this scale). Its real advantage is that Google runs the login endpoint and its abuse protection;
option B must supply its own rate limit, described below.

The price of option B is that the login check is our own code, which is the thing engineers are
taught to distrust. The design below keeps that code to one small, tested module, uses a
well-known library for the token, and states its limits in the README.

## Terms used in this note

- **Shared credential**: one password given to every reviewer. Nobody is identified individually.
- **Identity Platform**: Google Cloud's sign-in service for an application's end users. It is the
  same product as Firebase Authentication with paid extras; the browser library is the Firebase
  web SDK.
- **ID token**: a short signed text (a JWT, JSON Web Token) that a sign-in service gives the
  browser after login. It says who signed in and when it expires; a server checks the signature
  instead of asking the sign-in service each time.
- **Refresh token**: a long-lived secret the browser keeps so it can fetch a new ID token without
  the user logging in again.
- **Session token** (this design): the same idea as an ID token, but issued by our own proxy.
- **Bearer token**: a token sent in the `Authorization: Bearer ...` request header. JavaScript
  must attach it to each request on purpose.
- **Session cookie**: a token the browser stores and attaches to every request to that site
  automatically.
- **CSRF** (cross-site request forgery): another website makes the visitor's browser send a
  request to our API, and the browser attaches the cookie by itself, so the request looks logged
  in. It only works against automatic credentials (cookies), not against bearer tokens.
- **XSS** (cross-site scripting): an attacker gets their own JavaScript to run inside our page. It
  can then read anything the page's JavaScript can read, including a stored token.
- **CORS** (cross-origin resource sharing): the browser rule that a page on one origin (scheme,
  host and port) may call an API on another origin only if that API says so in response headers.
- **SameSite**: a cookie setting that controls whether the cookie is sent on requests that start
  from a different site.
- **MAU** (monthly active user): an account that signs in at least once in a month. Identity
  Platform is billed per MAU.
- **IAP** (Identity-Aware Proxy): a Google service that sits in front of an application and only
  lets signed-in, allow-listed people through.
- **HMAC**: a keyed checksum. Only someone with the key can produce a valid one, so it proves a
  token was issued by us and not altered.

## Option A: Identity Platform with one pre-created user

**Terraform.**

- `google_identity_platform_config` exists in the `hashicorp/google` provider. It is one per
  project. It can turn on email and password sign-in (`sign_in.email.enabled`,
  `password_required`), block self-signup (`client.permissions.disabled_user_signup`: "end users
  cannot sign up for a new account ... through any of our API methods"), block self-deletion, and
  list `authorized_domains`.
  [Provider documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/identity_platform_config.html.markdown)
- It **cannot be destroyed**. The documentation says: "This entity is created only once during
  intialization and cannot be deleted". The resource definition sets `exclude_delete: true`, and
  the generated delete function makes no API call; it logs "IdentityPlatform Config resources
  cannot be deleted from Google Cloud" and drops the resource from state.
  [Resource definition](https://github.com/GoogleCloudPlatform/magic-modules/blob/main/mmv1/products/identityplatform/Config.yaml),
  [provider source](https://github.com/hashicorp/terraform-provider-google/blob/main/google/services/identityplatform/resource_identity_platform_config.go)
- Creating it calls `identityPlatform:initializeAuth` and stops on any error.
  [Create template](https://github.com/GoogleCloudPlatform/magic-modules/blob/main/mmv1/templates/terraform/custom_create/identity_platform_config.go.tmpl).
  A community thread reports the error "Identity Platform has already been enabled for this
  project" when the resource is created a second time. If that is still true, a nightly
  destroy-then-apply in the same dev project would fail on the second night unless the resource is
  imported first. Not confirmed (see "Not verified").
- It needs a billing-enabled project, and it stores `client.api_key` in Terraform state in plain
  text (both stated in the provider documentation).
- `google_identity_platform_tenant` exists and can be deleted. A tenant is a separate pool of
  users inside one project. It has its own `allow_password_signup` and `disabled_user_signup`. It
  still depends on the undeletable project config (with `multi_tenant.allow_tenants`), so it does
  not solve the destroy problem.
  [Provider documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/identity_platform_tenant.html.markdown)
- **There is no Terraform resource for a user.** The provider documents config, tenant and
  identity-provider resources only; pages named `identity_platform_user` or
  `identity_platform_account` do not exist. The user must be created by a script calling the
  Identity Toolkit REST API (`accounts:signUp` with administrator credentials) or the Firebase
  Admin SDK.
  [REST reference (host not reachable from this session)](https://cloud.google.com/identity-platform/docs/reference/rest/v1/accounts/signUp)

**Cost.** Free below 50,000 MAU for email and password sign-in; a demo has one MAU.
[Pricing page](https://cloud.google.com/identity-platform/pricing) (figure taken from search
results; the page itself would not render here).

**Security for a shared credential.**

- Google's endpoint limits repeated wrong passwords and can hide whether an email exists. This is
  the one thing option A does better than option B.
- ID tokens last one hour and cannot be shortened. The web SDK renews them in the background with
  a refresh token that does not expire on its own, so a reviewer who logged in once stays logged
  in until the refresh tokens are revoked.
  [Manage user sessions](https://firebase.google.com/docs/auth/admin/manage-sessions) (via search
  results). Rotation therefore needs two admin calls: change the password, then revoke refresh
  tokens.
- The credential lives inside Identity Platform. Secret Manager would hold only a copy, and the
  two can drift.
- The token is a bearer token, so there is no CSRF exposure. The SDK keeps the tokens in browser
  storage, which JavaScript running in the page can read (the usual XSS exposure).
- Forgetting `disabled_user_signup = true` would let anyone create an account with the public API
  key and pass a naive "is the token valid" check. The proxy would also have to check the user ID.

**Effort and quick-start.** The page gains the Firebase SDK and build-time configuration (API key,
auth domain). The proxy verifies tokens against Google's public keys. A stranger must enable the
Identity Toolkit API and run a user-creation script after `terraform apply`. Local development
needs the Firebase emulator or a bypass switch.

**How it reads.** Standards-based, but it is a user directory with one row. A reviewer who checks
`terraform destroy` will find a leftover.

## Option B: shared password checked by `fhir-proxy` (recommended)

**Terraform.** Everything is an ordinary resource that is destroyed normally:

- `google_secret_manager_secret` for the password, and
  `google_secret_manager_secret_iam_member` giving only the proxy's service account
  `roles/secretmanager.secretAccessor` on that one secret.
- `google_secret_manager_secret_version` has a write-only argument, `secret_data_wo`. A
  write-only argument is sent to the API but never saved in Terraform state ("All arguments marked
  as write-only values will not be stored in the state: `secret_data_wo`"). This lets dev set the
  password from `tfvars` without breaking the brief's "no secret values in state" rule.
  [Provider documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/secret_manager_secret_version.html.markdown)
- A secret's optional `rotation` block does **not** rotate anything. It only sends a Pub/Sub
  reminder: "At `next_rotation_time`, Secret Manager will send a Pub/Sub notification".
  [Provider documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/secret_manager_secret.html.markdown).
  Not worth a topic for this project.

**Cost.** Secret Manager's free allowance covers a handful of versions and thousands of reads a
month (from memory). The check runs inside a service that already exists. $0 idle, $0 at demo scale.

**Security for a shared credential.**

- Brute force: nothing is built in, so the design supplies two layers (see the design section):
  a long random password that cannot be guessed online, and a rate limit as a backstop.
- Cookie or bearer token: **bearer token**. The dashboard will be on a CDN or Firebase domain and
  the proxy on `<name>.run.app`. The Public Suffix List (the browsers' list of domains under which
  unrelated parties register names) contains `*.run.app`, so every Cloud Run host counts as its
  own site and the two are cross-site.
  [Public Suffix List](https://github.com/publicsuffix/list/blob/main/public_suffix_list.dat).
  A cookie would have to be `SameSite=None`, which makes it a third-party cookie (blocked or
  partitioned by Safari and Firefox, from memory) and would need a CSRF defence on top. If D4
  picks Firebase Hosting with a rewrite to Cloud Run, the page and API share an origin, but
  community reports say Hosting forwards only a cookie named `__session`. A bearer token works the
  same in every hosting choice and has no CSRF exposure.
- XSS: a token in `sessionStorage` can be read by script injected into the page. The same is true
  of option A. The mitigations are the same either way: render HL7v2 and FHIR text as text, never
  as HTML, and send a strict Content-Security-Policy header.
- Self-signup: there is no account system, so nothing to disable.

**Effort and quick-start.** Proxy: one login endpoint, one check on every other route, a rate
limiter, and tests. Page: a password field and an API client that adds a header. Quick-start: set
one variable in `terraform.tfvars`; no console step, no extra API, and local mock mode needs
nothing.

**How it reads.** Proportionate. A shared demo password is what the requirement asks for; keeping
it in Secret Manager, out of state, with expiring signed tokens, rotation that revokes sessions and
a written threat model shows the judgment. The risk is that a reader sees "home-made auth", so the
README must say plainly what it is and is not (below).

## Option C: IAP directly on Cloud Run, and other ideas

**IAP on Cloud Run without a load balancer exists and is generally available.** Terraform:
`iap_enabled = true` on `google_cloud_run_v2_service`, plus
`google_iap_web_cloud_run_service_iam_member` with `roles/iap.httpsResourceAccessor` for each
person.
[Cloud Run service documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/cloud_run_v2_service.html.markdown),
[IAM resource documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/iap_web_cloud_run_service_iam.html.markdown),
[Google announcement](https://cloud.google.com/blog/products/serverless/iap-integration-with-cloud-run).
IAP itself is free and this route has no load balancer charge (per the announcement).

It does not survive a closer look for this project:

- **It admits named Google accounts, not a shared credential.** Each recruiter would need a
  Google account, and the author would need their address beforehand to allow-list it. The
  requirement is the opposite.
- **Outside users are awkward.** Google's page lists "The project must be within an organization"
  and "Identities must be from within the same organization" as limitations, and says users
  outside the organization, or projects with none, need a custom OAuth client made in the console.
  [Configure IAP for Cloud Run](https://cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)
  (via search results; the wording differed between page versions). The brief says no organization
  is required. The provider's old `google_iap_brand` and `google_iap_client` pages no longer
  exist, so that client is not a Terraform resource.
- **IAP without Google accounts means IAP plus Identity Platform** ("external identities"). That
  brings back all of option A, adds a hosted sign-in page, and switches off IAM checks
  (`gcip_settings`: "IAP will not enforce any IAM policies").
  [Provider documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/iap_settings.html.markdown)
- **It suits a server-rendered app, not a static page calling an API on another origin.** IAP
  answers an unauthenticated request with a redirect to Google sign-in, which a background
  `fetch` call cannot follow.

IAP remains the right answer if the audience were the author alone. It could be mentioned in the
README as the choice for staff access.

**Magic link or signed URL.** This is option B with the password carried in the link (for example
after the `#`, which browsers do not send to servers). It adds convenience, not security, and links
get forwarded and stored in browser history. Not recommended for the MVP; it can be added later on
top of option B without changing the proxy.

**Not a separate option but worth knowing:** Firebase Hosting can rewrite a path such as `/api/**`
to a Cloud Run service (`rewrites.run` on `google_firebase_hosting_version`, google-beta provider
only), which would put page and proxy on one origin and remove CORS. That belongs to decision D4.
[Provider documentation](https://github.com/hashicorp/terraform-provider-google/blob/main/website/docs/r/firebase_hosting_version.html.markdown)

## Design for option B

### What Terraform creates

- Module `identity`: the secret `reviewer-password` (no value), and the accessor binding for the
  `fhir-proxy` service account only.
- Module `identity`, optional: when the variable `reviewer_password` is set, one secret version
  written with `secret_data_wo`. The variable is `sensitive`, has a description, no default, and a
  validation block requiring at least 16 characters. `terraform.tfvars.example` carries a
  placeholder, never a working password.
  - dev: the cloner (or CI, from a GitHub secret) sets the variable. This is the brief's "default
    credential from `tfvars`".
  - prod: the variable is left unset, Terraform creates no version, and the script below sets it.
- Module `phr`: the `fhir-proxy` Cloud Run service with the secret mounted as a file, the
  settings `DASHBOARD_ORIGIN` and `SESSION_TTL_SECONDS` (default 28800), and a low
  `max_instance_count` (2). The service is publicly invocable, because the browser calls it
  directly; the README says so and says that the application check is the gate.

Why a mounted file and not an environment variable: Cloud Run reads an environment-variable
secret once when an instance starts, and Google recommends pinning a version in that case. A
mounted secret is fetched from Secret Manager when read, so a rotated password takes effect without
a redeploy. [Configure secrets for services](https://cloud.google.com/run/docs/configuring/secrets)
(via search results).

### What a script does

`scripts/secrets/` (task T27) gets `set-reviewer-password`: it reads the new password from a
no-echo prompt or stdin, refuses fewer than 16 characters, adds it as a new secret version, and
disables the older versions. It prints only a success line. The owner generates the password in a
password manager (24 random characters or more) and pastes it in, so the value never appears in a
terminal, a file or the repository.

### What the proxy does

- `POST /auth/login` with `{"password": "..."}`. The proxy compares it with the secret using a
  constant-time comparison (`hmac.compare_digest`; an ordinary `==` can leak, through timing, how
  many leading characters matched). On success it returns `{"token": "...", "expires_at": "..."}`.
  On failure it returns `401` with a fixed message.
- The token is a JWT signed with HMAC-SHA256 using the `PyJWT` library, with the accepted
  algorithm fixed to `HS256` when verifying. Claims: issuer, audience, issued-at, expiry. It
  carries no personal data.
- **The signing key is derived from the current password** (HMAC-SHA256 of a fixed label, keyed
  with the password). Consequences: there is one secret to manage, not two, and changing the
  password invalidates every outstanding token at once. This is sound only because the password is
  long and random, which the 16-character minimum and the README instruction enforce. The
  conventional alternative, a second secret holding an independent signing key, was considered; it
  needs a second rotation step and does not revoke sessions when the password changes.
- Every other route requires `Authorization: Bearer <token>` and returns `401` when it is
  missing, expired or wrongly signed. Exceptions: the CORS preflight (`OPTIONS`) and, by FHIR
  convention, the `CapabilityStatement` at `/metadata`.
- CORS: allow exactly `DASHBOARD_ORIGIN`, the `Authorization` and `Content-Type` headers, and no
  credentials. No cookie is ever set, so there is nothing for CSRF to ride on.
- If the secret has no version, login fails closed with `503` and a "reviewer login is not
  configured" message.
- Logs record failed logins (time, client address) and never the submitted value.

### What the page does

- A login view with one password field. On success it keeps the token in `sessionStorage`, which
  is cleared when the tab closes, and the typed API client adds the header to every call.
- On any `401` it clears the token and shows the login view again.
- Mock mode (task T16's "runs locally against mock data") skips the network and accepts any value.
- The hosting layer sends a Content-Security-Policy that allows scripts only from the page's own
  origin and connections only to the proxy.

### Session lifetime

Eight hours, fixed, with no renewal: long enough for an engineer's afternoon, and a token that
leaks is useless the next day. It is a variable. Changing the password ends all sessions
immediately.

### Rate limiting

Two layers, in order of importance:

1. **The password is not guessable.** At 24 random characters there are more possibilities than
   any online attack can try. This is the real defence, and it is why the minimum length is
   enforced in both the Terraform variable and the script.
2. **A limiter in the proxy** on failed logins: 5 a minute per client address and 60 a minute in
   total, answering `429` with `Retry-After`. Counters live in memory, so they are per instance;
   capping the service at 2 instances bounds the error to a factor of two and also caps cost. The
   per-address limit keeps one attacker from locking every reviewer out; the total limit bounds
   noise and cost.

Cloud Armor, Google's managed request filter, would do this outside the application, but it needs
a load balancer, which is billed hourly, so it is out on cost.

### Rotation

Run `set-reviewer-password` in prod after each round of applications, and at once if the password
is suspected to have spread. The new version is live within about a minute (the proxy re-reads the
mounted file, with a short cache), every old session stops working, and nothing is redeployed. Hand
the new password to the next reviewers.

### What the README should say

One short paragraph: the dashboard is behind a shared demo password, not per-user accounts; this
keeps casual visitors and crawlers away from the author's own heart-rate data; it does not identify
who viewed what; a real deployment with more than one patient would use per-user sign-in (SMART on
FHIR or an identity provider) and an audit log. Saying this is what makes the simple choice look
chosen.

## Consequences for tasks

- **T04 (module `identity`).** "Reviewer login resources" become: the `reviewer-password` secret,
  its accessor binding for the proxy's service account, and the optional write-only version for
  dev. No Identity Platform resources and no `identitytoolkit` API. Add an acceptance criterion:
  the password never appears in state (checked by searching a state file produced with a dummy
  value). Write-only arguments need Terraform 1.11 or later, so pin `required_version` accordingly.
- **T03 (module `project-base`), small.** Leave `identitytoolkit.googleapis.com` out of the
  default API list.
- **T14 (FHIR proxy read API).** Add the login endpoint, the bearer check, CORS and the limiter as
  one small module. Suggested acceptance criteria: wrong password gives `401`; a token that is
  expired, altered, or signed under the previous password gives `401`; the sixth failure in a
  minute from one address gives `429`; a missing secret version gives `503`; the comparison is
  constant-time; no log line contains the submitted password; the `CapabilityStatement` states
  the security scheme truthfully (not SMART on FHIR). Each test is break-checked as usual.
- **T16 (dashboard shell).** Login is a password-only form; token in `sessionStorage`; the API
  client adds the header and handles `401`; mock mode needs no backend. No Firebase SDK.
- **T22 (module `phr`).** Proxy is publicly invocable; mounts the secret; sets `DASHBOARD_ORIGIN`
  and `SESSION_TTL_SECONDS`; `max_instance_count = 2`. The hosting layer sets the
  Content-Security-Policy header. Record under D4 that Firebase Hosting rewrites would make page
  and proxy same-origin.
- **T27 (secret scripts).** Add `set-reviewer-password` as described.
- **T13 (cuff simulator), a gap this spike found.** The simulator is a second public Cloud Run
  service that the page calls, and its task has no authentication criterion. Either the page
  reaches it only through `fhir-proxy`, or it checks the same token (a small shared library and the
  same mounted secret). The first keeps one front door and is the simpler thing to explain. This
  needs an orchestrator decision; it applies whichever login option is chosen.
