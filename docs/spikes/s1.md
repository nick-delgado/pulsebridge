# Spike S1: can PulseBridge write vitals into OpenEMR over FHIR?

## Answer

**The Share button should call OpenEMR's FHIR API only; the REST vitals fallback is not needed.**
In OpenEMR 8.5.0, `POST /apis/default/fhir/Observation` accepts both a heart-rate Observation and a
blood-pressure panel (both returned `201 Created`), stores them in the `form_vitals` table as a
Vitals form on an encounter, shows them in the patient chart, and returns them from
`GET .../fhir/Observation`.

Three things differ from what the brief assumes, and each changes the design:

1. **An Encounter is required.** OpenEMR stores vitals as a form attached to a visit ("encounter").
   An Observation without `encounter` is rejected with `400`. The share flow must create (or find)
   an Encounter first: `POST /apis/default/fhir/Encounter`, which works.
2. **Conditional create is not honoured for Patient.** The `If-None-Exist` header is silently
   ignored and a repeat POST creates a duplicate patient. The share flow must search first
   (`GET /fhir/Patient?identifier=...`) and create only if nothing comes back.
3. **There is no Bundle endpoint.** The share is a sequence of single-resource calls
   (search Patient, maybe create Patient, create Encounter, create each Observation), not one
   transaction Bundle.

Authentication works as hoped with no user and no password: a backend client registered with a
public key gets a 5-minute token through the OAuth2 client credentials grant, limited to six
`system/...` scopes.

## Terms used

- **Observation / Patient / Encounter**: FHIR resource types. An Observation is one measurement,
  a Patient is the person, an Encounter is a visit or contact with the clinic.
- **Conditional create**: a FHIR feature where the client sends a create with a search condition in
  the `If-None-Exist` header, and the server creates the resource only if no match exists. It makes
  a create safe to repeat.
- **OAuth2 client**: a program registered with the server so it can ask for access tokens.
- **Scope**: a string naming one permission a token carries, for example `system/Observation.write`.
  The server refuses calls the token's scopes do not cover.
- **Client credentials grant**: the OAuth2 flow for server-to-server calls. The client proves its own
  identity and gets a token; no human logs in.
- **`private_key_jwt`**: the way the client proves its identity in that flow here. It signs a short
  JSON Web Token (JWT, a signed JSON document) with its private key; the server checks the signature
  against the public key the client registered.
- **JWKS**: JSON Web Key Set, the JSON format for publishing public keys.
- **Dynamic client registration**: an HTTP endpoint where a client registers itself by posting its
  metadata, instead of an administrator typing it into a screen.

## Findings

### 1. Does `POST /fhir/Observation` accept vital signs? Yes

The `CapabilityStatement` (`GET $B/apis/default/fhir/metadata`, the server's self-description) lists
`create` and `update` for Observation, Patient and Encounter.

**(a) Heart rate** (LOINC 8867-4, UCUM `/min`):

```
curl -k -X POST $B/apis/default/fhir/Observation \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/fhir+json" -d @hr.json
```

```json
{"resourceType":"Observation","status":"final",
 "category":[{"coding":[{"system":"http://terminology.hl7.org/CodeSystem/observation-category","code":"vital-signs"}]}],
 "code":{"coding":[{"system":"http://loinc.org","code":"8867-4","display":"Heart rate"}]},
 "subject":{"reference":"Patient/a337dc1b-d192-46c5-9a91-18b765ec4fb6"},
 "encounter":{"reference":"Encounter/a337dc2d-14eb-4f5a-b437-eb29b270afbc"},
 "effectiveDateTime":"2026-11-13T09:30:00+00:00",
 "valueQuantity":{"value":72,"unit":"beats/minute","system":"http://unitsofmeasure.org","code":"/min"},
 "device":{"display":"Synthetic wrist wearable"},
 "identifier":[{"system":"urn:pulsebridge:observation","value":"hr-synthetic-0001"}]}
```

Response: `HTTP 201`, `Content-Type: application/json`, body `{"uuid":"a337dc3f-e1fd-48e8-b577-ed437cc3cc77"}`.

**(b) Blood pressure panel** (LOINC 85354-9, components 8480-6 and 8462-4, `mm[Hg]`): same request
shape, with no `valueQuantity` and

```json
"component":[
 {"code":{"coding":[{"system":"http://loinc.org","code":"8480-6"}]},
  "valueQuantity":{"value":128,"unit":"mmHg","system":"http://unitsofmeasure.org","code":"mm[Hg]"}},
 {"code":{"coding":[{"system":"http://loinc.org","code":"8462-4"}]},
  "valueQuantity":{"value":82,"unit":"mmHg","system":"http://unitsofmeasure.org","code":"mm[Hg]"}}]
```

Response: `HTTP 201`, body `{"uuid":"a337dc3f-e213-47e6-a3d7-fde43c2234bd"}`.

The create response is not standard FHIR: there is no `Location` header and the body is a bare
`{"uuid": ...}` rather than the Observation. The uuid is the Observation id.

Rejections observed (all `HTTP 400` with a `validationErrors` object, not a FHIR `OperationOutcome`):

| Request | Response message |
|---|---|
| No `encounter` | `Observation.encounter must reference an Encounter; vitals are stored as an encounter form` |
| No `category` | `Observation.category is required to route a write; it decides which store the code belongs to` |
| Same code, same encounter, same `effectiveDateTime` posted twice | `A "8867-4" reading already exists for this encounter at this effectiveDateTime (Observation/a337dc3f-...); POST does not overwrite a stored reading -- update that Observation with PUT` |
| `valueQuantity.code` = `{beats}/min` | `Observation.valueQuantity has unit "{beats}/min" which cannot be converted to "/min"` |
| `subject` is a different patient from the encounter's | `Encounter does not belong to the patient named in Observation.subject` |

Also observed: a decimal value (75.5) is accepted; a quantity with only `"unit":"bpm"` and no UCUM
code is accepted; `PUT /fhir/Observation/{uuid}` changing 72 to 74 returned `200` with the full
Observation and updated the row. `If-None-Exist` on Observation was not tested (the duplicate
check above already refuses a repeat).

### 2. Where does it land? In the Vitals form, and it reads back

Database after the two POSTs (one row, because both readings share an encounter and a timestamp):

```
form_vitals: id=1 date=2026-11-13 09:30:00 pid=3 user=oe-system bps=128 bpd=82 pulse=72.000000
forms:       encounter=2 form_name=Vitals form_id=1 formdir=vitals pid=3
```

- Readings with the same encounter and `effectiveDateTime` are merged into one `form_vitals` row.
  Each new timestamp creates a new row and a new Vitals form on the encounter.
- `effectiveDateTime` is converted to the server's time zone (UTC here):
  `2026-11-12T23:00:00-05:00` was stored as `2026-11-13 04:00:00`. A reading dated outside the
  encounter's period was still accepted.
- The row's author is `oe-system` ("System Operation User"), the built-in account that
  client-credentials tokens act as.

Read back by id (`GET $B/apis/default/fhir/Observation/a337dc3f-e1fd-...`, `HTTP 200`, trimmed):

```json
{"id":"a337dc3f-e1fd-48e8-b577-ed437cc3cc77","resourceType":"Observation","status":"final",
 "meta":{"profile":["http://hl7.org/fhir/StructureDefinition/heartrate", "...us-core-heart-rate|8.0.0"]},
 "code":{"coding":[{"system":"http://loinc.org","code":"8867-4","display":"Heart rate"}]},
 "subject":{"reference":"Patient/a337dc1b-...","type":"Patient"},
 "encounter":{"reference":"Encounter/a337dc2d-...","type":"Encounter"},
 "effectiveDateTime":"2026-11-13T09:30:00+00:00",
 "valueQuantity":{"value":72,"unit":"/min","system":"http://unitsofmeasure.org","code":"/min"}}
```

The blood pressure read back with both components (128 and 82, `mm[Hg]`).

What is lost on the round trip: `device`, `identifier` and `performer` were not returned, the
`display` text and `unit` text were rewritten by OpenEMR. OpenEMR keeps only the numbers, the
patient, the encounter and the time.

Search (`GET $B/apis/default/fhir/Observation?patient={uuid}&category=vital-signs`) returned
**16 Observations for that single row**: one per vital-sign type OpenEMR knows, most of them empty
with a `dataAbsentReason` ("no value recorded"), plus a vital-signs panel and a calculated average
blood pressure (LOINC 96607-7). Searching with `&code=8867-4` returns just the heart rates.

UI: logged in as the admin user with `curl` and fetched the server-rendered pages. The encounter's
form list showed `Vitals (by System Operation User) ... Blood Pressure: 128/82 Pulse: 74 per min`,
and the Vitals card on the patient summary showed `Most recent vitals from: 2026-11-13 09:43:00
Pulse: 72 per min`. The 75.5 reading is displayed rounded, as `76 per min`.

### 3. REST fallback: works, but only with a user login, so it is the worse option

Not needed, tested for completeness.

- With the client-credentials token, `GET $B/apis/default/api/patient/3/encounter/2/vital` returned
  `403` (`API call failed due to insufficient permissions`). The standard REST API has only
  `user/vital.*` scopes, no `system/vital.*`, so a backend client cannot use it.
- It needs: the `rest_api` setting on, an encounter (the path contains the encounter number), and a
  token for a real user. The only non-browser way to get a user token is the password grant, which
  must be switched on (`oauth_password_grant`) and cannot be self-registered: the registration
  endpoint silently replaced `grant_types: ["password"]` with `["authorization_code"]`, and the
  grant had to be set in the `oauth_clients` table by hand. The token then lasts 3600 seconds.
- With that user token, `POST $B/apis/default/api/patient/3/encounter/2/vital` with
  `{"bps":"131","bpd":"84","pulse":"66"}` returned `201 {"vid":8,"fid":9}`. With no `date` the row
  is stamped with the current time; a `"date":"2026-11-10 08:00:00"` field is honoured.
- The path takes the numeric patient id and encounter number. Using the uuids instead still returned
  `201` but wrote an orphan row with `pid=0`.
- Rows written this way are readable through FHIR: the Observation search returned the 131/84 and
  119/79 panels.

### 4. Patient: create works, conditional create does not

```
curl -k -X POST $B/apis/default/fhir/Patient -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/fhir+json" -H "If-None-Exist: identifier=PB-SYN-0002" -d @patient.json
```

```json
{"resourceType":"Patient",
 "identifier":[{"use":"official",
   "type":{"coding":[{"system":"http://terminology.hl7.org/CodeSystem/v2-0203","code":"PT"}]},
   "system":"urn:pulsebridge:patient","value":"PB-SYN-0002"}],
 "name":[{"use":"official","family":"Sharewell","given":["Pat"]}],
 "gender":"male","birthDate":"1975-06-07"}
```

First call: `HTTP 201 {"pid":3,"uuid":"a337dc1b-d192-46c5-9a91-18b765ec4fb6"}`.
Identical second call, same header: `HTTP 201 {"pid":4,"uuid":"a337dc1c-ed81-4da0-8b2b-0fbdb62466dc"}`.
The database then held two rows with the same external id. **`If-None-Exist` is ignored.**

Search-then-create that works:

```
curl -k "$B/apis/default/fhir/Patient?identifier=PB-SYN-0002" -H "Authorization: Bearer $TOKEN"
```

Returns a Bundle with `total: 1` when the patient exists and `total: 0` when not. The match is
exact (`PB-SYN-000` matched nothing). The system part is ignored: `urn:pulsebridge:patient|PB-SYN-0002`
and `http://terminology.hl7.org/CodeSystem/v2-0203|PB-SYN-0002` matched too.

Details that matter:

- The identifier is stored only if it carries `type.coding.code = "PT"`; it goes into OpenEMR's
  "external ID" field (`pubpid`). A first attempt with a plain system-and-value identifier returned
  `201` but dropped the identifier, and the patient could not be found by it afterwards.
- OpenEMR does not keep the identifier's `system`. On read it comes back as
  `http://terminology.hl7.org/CodeSystem/v2-0203`.
- Required fields: first name, last name, gender and birth date. The name must have
  `"use":"official"`; without it the name was not read and the call failed with
  `First Name must not be empty`. Errors are `400` with `validationErrors`, e.g.
  `{"sex":{"NotEmpty::EMPTY_VALUE":"Gender must not be empty"}}`.
- Search-then-create is not atomic: two shares at the same moment could both find nothing and both
  create.

### 5. OAuth2: client credentials with a registered public key

What worked and what did not:

| Attempt | Result |
|---|---|
| Registration while the API settings are off | `404 {"message":"OpenEMR Error: API is disabled"}` |
| Registration (`POST $B/oauth2/default/registration`, no authentication needed) with `grant_types: ["client_credentials"]`, a `jwks` and `system/` scopes | `200`; client stored with `is_enabled = 0` |
| Token request before the client is enabled | `401 invalid_client` |
| Token request after `UPDATE oauth_clients SET is_enabled = 1` | `200`, `expires_in: 300`, no refresh token |
| Client credentials with the client secret instead of a signed JWT (form field or Basic header) | `400 invalid_request`, hint `assertion type is not supported` |
| Signed JWT whose `aud` is not OpenEMR's own token URL | `400 invalid_client` (log: `not allowed to be used by this audience`) |
| Asking for a scope the client did not register | Token issued, extra scope silently left out |
| Password grant | Only after an admin-side change, and it needs a user's password (see finding 3) |
| Authorization code grant | Not tested; it needs a person at a browser, so it does not fit a backend service |

Settings (rows in the `globals` table; all default to off):

| Setting | Needed for | Default |
|---|---|---|
| `rest_fhir_api` = 1 | The FHIR API and the registration endpoint | 0 |
| `rest_system_scopes_api` = 1 | `system/...` scopes; without it none are offered | 0 |
| `site_addr_oath` = OpenEMR's public base URL | Fixes the issuer and the expected token `aud` | empty (then derived from the request's host) |
| `rest_api` | Standard REST API only; **not** needed for the FHIR path | 0 |

Two non-interactive ways to set them, both verified:

- Container environment variables `OPENEMR_SETTING_<name>=<value>`. The image's start script runs
  `UPDATE globals SET gl_value=... WHERE gl_name=...` for each one on every start (log line
  `Set rest_fhir_api to 1`). Verified by turning the settings off, recreating the container with
  the three variables, and repeating a token request and an Observation POST.
- SQL directly: `UPDATE globals SET gl_value='1' WHERE gl_name='rest_fhir_api';`. Took effect on the
  next request.

Scopes: the client was registered with

```
system/Patient.read system/Patient.write
system/Encounter.read system/Encounter.write
system/Observation.read system/Observation.write
```

A token with only the three `.write` scopes could create an Observation (`201`) but got `401` on
the Patient search, so `.read` is needed on Patient for search-then-create. `Encounter.read` and
`Observation.read` are needed only to reuse an encounter or to read results back. A token with
only `system/Observation.read` got `401` on POST.

Token lifetime: 300 seconds for client credentials (a constant in OpenEMR's
`AuthorizationController`), no refresh token; the client simply asks again. Other grants get 3600
seconds.

### 6. Surprises that affect the design

- **Encounter needed** (above). `POST /fhir/Encounter` with `status`, `class` (`AMB`), `subject`
  and `period` returned `201`. The response is OpenEMR's own JSON, not FHIR, and usefully contains
  the encounter uuid (`euuid`), the encounter number (`encounter`) and the numeric patient id (`pid`).
- **Responses to writes are not FHIR.** No `Location` header, no resource body, errors are
  `validationErrors` objects rather than `OperationOutcome`. Content type is `application/json`.
- **Ids are UUIDs** for Patient, Encounter and Observation. The numeric `pid` appears only in the
  Patient-create and Encounter-create responses; the FHIR Patient resource does not contain it.
- **Chart link**: `https://<openemr>/interface/patient_file/summary/demographics.php?set_pid=<pid>`
  opened the right chart for a logged-in session. It needs the numeric `pid`, and the reviewer must
  be logged in to OpenEMR.
- **A repeated share is refused, not duplicated.** The duplicate `400` names the existing
  Observation id, which makes Observation writes safely repeatable.
- **No `POST` to the FHIR base**: a transaction Bundle returned `403`.
- **Provenance is read-only** in OpenEMR (only `system/Provenance.read`/`.rs` are useful; no create
  route), and `device` on an Observation is dropped. Source attribution does not survive the share.
- **Startup race**: started at the same moment as MariaDB, the OpenEMR container failed with
  `ERROR: unable to connect to database as root` and exited. Started after the database was
  ready, first boot took about 20 seconds on this machine.
- **Registration is open**: anyone who can reach `/oauth2/default/registration` can register a
  client. It stays disabled until approved, but the endpoint is public.
- OpenEMR logged one server-side error while saving its calculated average blood pressure
  (`Failed to save calculated record ... Duplicate entry`). The request still returned `201`.

## OAuth2 recipe for a provisioning script

1. Start MariaDB and wait until it accepts connections. Then start OpenEMR with
   `OPENEMR_SETTING_rest_fhir_api=1`, `OPENEMR_SETTING_rest_system_scopes_api=1` and
   `OPENEMR_SETTING_site_addr_oath=<public base URL of OpenEMR>`.
2. Wait until `GET <base>/apis/default/fhir/metadata` returns `200`.
3. Generate an RSA 2048-bit key pair. Keep the private key out of the repo and out of Terraform
   state (Secret Manager). Write the public key as a JWKS: `{"keys":[{"kty":"RSA","kid":"<key id>",
   "use":"sig","alg":"RS384","n":"...","e":"AQAB"}]}`.
4. Register: `POST <base>/oauth2/default/registration`, `Content-Type: application/json`, body:
   `application_type: "private"`, `client_name`, `redirect_uris` (required by the endpoint even
   though unused; any https URL), `token_endpoint_auth_method: "private_key_jwt"`,
   `grant_types: ["client_credentials"]`, `scope` (the six scopes above, space-separated), `jwks`
   (the object from step 3). Expect `200`.
5. From the response keep `client_id`. The response also contains a `client_secret` and a
   `registration_access_token`; neither is used by this flow. Do not log the response.
6. Enable the client: `UPDATE oauth_clients SET is_enabled = 1 WHERE client_id = '<client_id>';`
   run against the OpenEMR database (for example `docker exec` into the MariaDB container).
7. At share time, build a JWT signed with the private key, algorithm RS384, header `kid` matching
   the JWKS, claims `iss` = `sub` = `client_id`, `aud` = `<site_addr_oath>/oauth2/default/token`,
   `exp` about 60 seconds ahead, `jti` a fresh random id.
8. `POST <base>/oauth2/default/token`, form-encoded:
   `grant_type=client_credentials`, `scope=<scopes>`,
   `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`,
   `client_assertion=<the JWT>`. Expect `200` with `access_token`, `token_type: Bearer`,
   `expires_in: 300`.
9. Call the API with `Authorization: Bearer <access_token>`. Get a new token when it expires.

## Design consequences

### T15 (proxy share-to-OpenEMR)

- Call sequence per share: get token; `GET Patient?identifier=<id>`; if `total` is 0,
  `POST Patient`; `POST Encounter` (or reuse one found with `GET Encounter?patient=<uuid>&date=<day>`,
  which returned the encounter in the test); `POST Observation` for each reading with `subject` and
  `encounter` set.
- The acceptance criterion "sharing the same reading twice does not create a duplicate patient"
  must be met by search-then-create. `If-None-Exist` may still be sent, but it does nothing.
- The Patient sent to OpenEMR needs a `PT`-typed identifier, a name with `use: official`, gender
  and birth date.
- Treat the duplicate-reading `400` as "already shared", not as a failure.
- The trace panel will show `201` responses with small non-FHIR bodies and no `Location`. If the
  trace should show the stored Observation, follow each create with a `GET` by uuid.
- Units must be exactly `/min` and `mm[Hg]` in `valueQuantity.code`.
- The chart link needs the numeric `pid`; take it from the Encounter-create response.
- The proxy holds a private key, not a client secret. It signs a new assertion every 5 minutes at
  most. The trace must not show the assertion or the token.
- `aud` in the assertion must equal the `site_addr_oath` value, so the proxy needs that URL as
  configuration even if it reaches OpenEMR by another address.
- `device` and `Provenance` will not be visible in OpenEMR. They remain in PulseBridge's own store.

### T23 (openemr Terraform module / client registration script)

- Set the three `OPENEMR_SETTING_*` variables on the container. `rest_api` stays off.
- Order the containers (health check on MariaDB, restart policy on OpenEMR) because of the startup
  race.
- The registration script follows the recipe above. The secret to store in Secret Manager is the
  **private key**, plus the `client_id` as plain configuration. This changes the acceptance
  criterion "the client secret goes to Secret Manager": the secret is now a key.
- Enabling the client needs database access from the script (step 6).
- The registration endpoint is unauthenticated. Consider restricting who can reach
  `/oauth2/default/registration` at the firewall or reverse proxy once the client exists.
- Pin the image by digest; tags are rebuilt daily.

### Proposed edits to the brief (for the orchestrator)

- Data flow step 4: replace "conditional create on an identifier" with "search by identifier, then
  create if absent", and add "creates an Encounter for the share".
- Dashboard item "Bundle sent": OpenEMR accepts no Bundle; the trace shows individual requests.
- Secrets row: "OpenEMR client secret" becomes "OpenEMR client private key".
- Open question "OpenEMR FHIR write support": resolved, FHIR Observation POST, no fallback.

## What was not verified

- The chart in a real browser. The UI check was `curl` against server-rendered pages with an admin
  session.
- Enabling the client or the settings through the admin screens; only SQL and environment variables
  were used. Whether editing `oauth_clients` directly is considered supported by OpenEMR is unknown.
- Registration with `jwks_uri` (a URL to the keys) instead of inline `jwks`, and key rotation.
- The authorization code grant, token revocation and introspection.
- `If-None-Exist` on Observation and Encounter; `PUT` on Patient.
- `site_addr_oath` with a real host name and certificate. Only tested: with it set, a token request
  arriving on a different local address and port still succeeded.
- Whether the image's `8.5.0` tag is what the OpenEMR project calls its current stable release; the
  choice rests on `latest` pointing at it.
- Other OpenEMR versions, and behaviour on the e2-micro (that is spike S2).
- Concurrent shares (the non-atomic patient search-then-create).
- Why `form_vitals.authorized` is 0 on API-written rows and whether any screen filters on it.
- The cause of the logged `Failed to save calculated record` error.
- Writing a Device resource and referencing it; other vital signs (SpO2, temperature, weight).
