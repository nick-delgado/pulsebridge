# Spike S2: OpenEMR + MariaDB + MLLP adapter on one e2-micro

Run on 2026-11-13 against a real GCP project (`<project-id>`), one VM, about 67 minutes of VM time.
The VM and its disk were deleted afterwards (see "Cleanup").

## Verdict

**Yes with caveats: the e2-micro is acceptable for a demo.** No e2-small comparison was run
because the e2-micro did not fail.

What works:

- OpenEMR 8.5.0 completed first-time setup three times out of three, stayed up, and came back
  unattended after a reboot. There were **zero OOM kills** in every run, including a run with swap
  switched off.
- Memory is not the tight constraint the brief feared. With all three containers idle the VM had
  216 to 330 MB of memory still available and used 0 to 140 MB of the 2 GB swap.
- When the VM has been quiet, responses are fast: login page about 0.07 s, FHIR metadata about
  0.31 s, authenticated FHIR read about 0.08 s (medians, measured inside the VM).

The caveats, in order of importance:

1. **CPU, not memory, is the limit.** An e2-micro is a "shared-core" machine: it may use its two
   virtual CPUs at full speed only in short bursts. After roughly 20 to 30 seconds of sustained
   work, everything became about 8 times slower (login 0.07 s to 0.5 s, FHIR metadata 0.31 s to
   2.5 s) until the VM had been idle for a few minutes. A single reviewer clicking around is fine;
   a load test, or two people at once, is not.
2. **First boot takes about 5 minutes** (269 to 331 s) before OpenEMR answers, plus about 8 minutes
   to download the 3.6 GB OpenEMR image, plus under a minute to install Docker. Budget **about 15
   minutes from `terraform apply` to a usable OpenEMR**. Later reboots take 43 s.
3. **The first request after an idle period is slow**: 1 to 2 s for the login page, up to 2 s for
   FHIR metadata, because idle memory pages were moved to swap or dropped from cache.
4. **Apache must be capped** (see "Settings that mattered"). With the image's stock settings a
   small burst of requests started 38 PHP worker processes and pushed 223 MB into swap.

Terms used in this document:

- **Swap**: a file on disk the kernel uses as overflow when RAM is full. It prevents crashes but
  is far slower than RAM, especially on the free tier's standard (spinning-disk class) disk.
- **OOM kill**: "out of memory" kill. When RAM and swap are both exhausted, the Linux kernel
  terminates a process to survive. It is logged in the kernel log (`dmesg`).
- **RSS**: "resident set size", the amount of physical RAM a process is holding right now.
- **Cold / warm**: cold is the first request after a start or an idle period; warm is a request
  repeated straight after, when code and data are already in memory.

exclude internet latency. "Tuned" means the settings in the next section.

### Bursts of 20 parallel requests (200 login + 60 metadata)

| Run | Wall time | Login median / worst | Metadata median / worst | Peak `httpd` processes | Lowest available RAM | Peak swap |
|---|---|---|---|---|---|---|
| Tuned, after 8 min idle | 22 s | 1.02 / 2.01 s | 3.33 / 3.82 s | 5 | 158 MB | 36 MB |
| Tuned, repeated immediately | 136 s | 1.04 / 10.26 s | 33.99 / 39.51 s | 5 | 159 MB | 67 MB |
| Stock settings (CPU allowance already partly used) | 135 s | 1.19 / 8.52 s | 35.50 / 46.22 s | 38 | 120 MB | 223 MB |
| Tuned, swap off (CPU allowance already partly used) | 107 s | 0.98 / 1.49 s | 33.52 / 38.00 s | 5 | 135 MB | 0 |

No request failed in any run. The first two rows are the clean demonstration of the CPU limit:
identical configuration, the second run six times slower. The guest's own "steal" counter stayed
at 0 throughout, so this throttling is invisible from inside the VM. The slowdown is consistent
with how Google describes shared-core machines, but it was not confirmed in Cloud Monitoring.

## Settings that mattered

| Setting | Stock | Used | What difference it made |
|---|---|---|---|
| Apache `MaxRequestWorkers` (how many PHP worker processes may exist at once) | 250, starts 5 | 4, starts 2 | The one that matters. Under the 20-parallel burst stock grew to 38 processes and 223 MB of swap; capped it stayed at 5 processes and 36 to 67 MB. Idle `httpd` count drops from 7 to 3. |
| MariaDB `innodb_buffer_pool_size` (RAM reserved for caching table data) | 128 MB | 64 MB | Small. MariaDB's memory at idle was about the same either way (155 MB stock vs 119 to 179 MB tuned) because a fresh OpenEMR database does not fill even 64 MB. It is a ceiling worth keeping as data grows. |
| MariaDB `performance_schema`, `max_connections`, small buffers | off, 151, larger | off, 30, smaller | No measurable effect at idle. `performance_schema` is already off by default in this image. |
| 2 GB swap file | none | 2 GB | Not needed to survive: the tuned stack booted, ran and took the burst with swap off and no OOM kill. It is cheap insurance against a spike, so keep it. |
| `vm.swappiness` (how eagerly the kernel moves idle memory to swap) | 60 | 60 (unchanged) | Not changed. Other values were not tested. |
| PHP `memory_limit`, opcache | 512 MB, opcache on, JIT buffer 100 MB | unchanged | Left alone. With at most 4 workers the per-request limit cannot exhaust the VM in normal use. |

### Compose file (as run; reusable by T21)

Secrets are read from a `.env` file beside it. Images are pinned by digest so a rebuild gets the
same bytes.

```yaml
services:
  mariadb:
    image: mariadb:11.8@sha256:d36f18d65a0459510b8b0f643b226a6d299e3206486e2b64ff20754a6d291707
    restart: always
    command:
      - mariadbd
      - --character-set-server=utf8mb4
      - --innodb-buffer-pool-size=64M
      - --innodb-log-buffer-size=8M
      - --performance-schema=OFF
      - --max-connections=30
      - --table-open-cache=400
      - --key-buffer-size=8M
      - --tmp-table-size=16M
      - --max-heap-table-size=16M
      - --thread-cache-size=4
    environment:
      MARIADB_ROOT_PASSWORD: ${DB_ROOT_PASS}
    volumes:
      - dbdata:/var/lib/mysql
    healthcheck:
      test: [CMD, /usr/local/bin/healthcheck.sh, --su-mysql, --connect, --innodb_initialized]
      start_period: 2m
      start_interval: 10s
      interval: 1m
      timeout: 10s
      retries: 3
  openemr:
    image: openemr/openemr:8.5.0-2026-11-12@sha256:f9536d0bcad7956d21471e73b91690215ad00ee4aed9448770e5012df15318cd
    restart: always
    ports:                      # loopback only in the spike; T21 decides real exposure
      - 127.0.0.1:80:80
      - 127.0.0.1:443:443
    environment:
      MYSQL_HOST: mariadb
      MYSQL_ROOT_PASS: ${DB_ROOT_PASS}
      MYSQL_USER: openemr
      MYSQL_PASS: ${DB_OE_PASS}
      OE_USER: admin
      OE_PASS: ${OE_ADMIN_PASS}
    volumes:
      - sites:/var/www/localhost/htdocs/openemr/sites
      - logs:/var/log
      - ./apache-lowmem.conf:/etc/apache2/conf.d/zz-lowmem.conf:ro
    depends_on:
      mariadb:
        condition: service_healthy
  mllp:
    image: gcr.io/cloud-healthcare-containers/mllp-adapter@sha256:92eaa0fc5fcd0eb7ff62bd28c9140dcd7582bfec20790e5b203ca8dc75c4a90f
    restart: always
    network_mode: host
    command:
      - /usr/mllp_adapter/mllp_adapter   # the image has no entrypoint; the binary must be named
      - --port=2575
      - --receiver_ip=127.0.0.1          # spike only; S4/T21 set the real listen address
      - --hl7_v2_project_id=${GCP_PROJECT}
      - --hl7_v2_location_id=us-central1
      - --hl7_v2_dataset_id=<dataset-id>
      - --hl7_v2_store_id=<store-id>
      - --export_stats=false             # default true sends metrics to Cloud Monitoring
      - --logtostderr
volumes:
  dbdata:
  sites:
  logs:
```

`apache-lowmem.conf` (loaded last because of its `zz-` name, so it overrides the image's
`mpm.conf`):

```apache
StartServers            2
MinSpareServers         1
MaxSpareServers         2
MaxRequestWorkers       4
MaxConnectionsPerChild  500
```

### Startup script fragments

Swap and Docker (runs on every boot, safe to repeat):

```bash
if [ ! -f /swapfile ]; then
  fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile >/dev/null
  echo '/swapfile none swap sw 0 0' >> /etc/fstab
fi
swapon -a
if ! command -v docker >/dev/null; then
  export DEBIAN_FRONTEND=noninteractive
  apt-get update -qq && apt-get install -y -qq ca-certificates curl jq
  install -m 0755 -d /etc/apt/keyrings
  curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
  echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/debian bookworm stable" \
    > /etc/apt/sources.list.d/docker.list
  apt-get update -qq
  apt-get install -y -qq docker-ce docker-ce-cli containerd.io docker-compose-plugin
fi
```

Secrets file. In the spike the passwords were generated on the VM and never left it; T21 should
read them from Secret Manager instead:

```bash
umask 077
MD=http://metadata.google.internal/computeMetadata/v1
{ echo "DB_ROOT_PASS=<from Secret Manager>"
  echo "DB_OE_PASS=<from Secret Manager>"
  echo "OE_ADMIN_PASS=<from Secret Manager>"
  echo "GCP_PROJECT=$(curl -sf -H 'Metadata-Flavor: Google' $MD/project/project-id)"; } > /opt/edge/.env
docker compose -p edge --project-directory /opt/edge up -d
```

Readiness check used for the timings (also a good health check for the status strip):

```bash
curl -sk -o /dev/null -w '%{http_code}' https://127.0.0.1/meta/health/readyz   # 200 when ready
```

### Enabling the FHIR API and getting a token (OpenEMR 8.5.0)

The production image did not act on `OPENEMR_SETTING_*` environment variables for these
switches (only the development images' compose files use them), so the spike set them in the
`globals` table after setup:

```sql
REPLACE INTO globals (gl_name, gl_index, gl_value) VALUES
  ('site_addr_oath', 0, 'https://localhost'),   -- the public base URL; required for OAuth2
  ('rest_api', 0, '1'),
  ('rest_fhir_api', 0, '1'),
  ('rest_system_scopes_api', 0, '1'),
  ('oauth_password_grant', 0, '3');             -- spike only
```

Client registration and enabling:

```bash
curl -sk -X POST -H 'Content-Type: application/json' https://localhost/oauth2/default/registration \
  --data '{"application_type":"private","redirect_uris":["https://localhost/callback"],
           "client_name":"<name>","token_endpoint_auth_method":"client_secret_post",
           "scope":"openid api:fhir user/Patient.read user/Patient.write user/Observation.read"}'
# new clients are disabled until an administrator enables them:
#   UPDATE oauth_clients SET is_enabled=1 WHERE client_id='<client-id>';
```

Two things here were not obvious and cost time:

- **OpenEMR 8.5.0 silently drops `password` from `grant_types` at registration.** It is an
  administrator-only grant. The spike added it directly in the database
  (`grant_types='authorization_code|password'`). Without that the token endpoint answers
  `400 unauthorized_client: Grant type password is not registered for this client`.
- **Confidential clients must send `client_secret` on the password grant** from 8.5.0 on, or
  they get `401 invalid_client`.

## Design consequences

For **T21 (edge-vm Terraform module)**:

- Keep `e2-micro`, 30 GB `pd-standard`, 2 GB swap. Reuse the compose file and
  `apache-lowmem.conf` above.
- The Apache cap is required, not optional. The MariaDB flags are a safety ceiling.
- Pin images by digest. The MLLP adapter has no version tags at all, only `latest`, so a digest
  is the only way to pin it.
- The MLLP adapter image has no entrypoint, so the command must start with
  `/usr/mllp_adapter/mllp_adapter`. Its `--api_addr_prefix` flag is deprecated and can be dropped.
  Its default `--export_stats=true` writes to Cloud Monitoring; decide deliberately whether the
  VM's service account should be allowed to do that.
- `restart: always` plus the fstab swap entry was enough for unattended recovery after a reboot.
- Anything that waits for OpenEMR (provisioning script, a Terraform check, the status strip)
  must tolerate about 15 minutes on first apply. Poll `/meta/health/readyz`.
- The startup script must be idempotent: it runs on every boot.
- The VM's disk holds the clinic database. Destroying the VM destroys it; decide whether the
  data volumes belong on a separate persistent disk, as the brief's layout suggests.

For **T23 (OpenEMR module and OAuth2 client provisioning)**:

- Enabling the FHIR API, setting the site address, and enabling the registered client all needed
  database writes in this spike. The provisioning script needs database access (or an
  administrator session), not only the HTTP API.
- `site_addr_oath` must be the URL the FHIR proxy will actually call. `https://localhost` only
  worked because the spike called from the VM itself.
- OpenEMR serves a self-signed certificate. The FHIR proxy needs a plan for certificate
  verification (trust that certificate, or put a real one in front).
- Do not build Share on the password grant. For a server-to-server caller, OpenEMR's documented
  route is `client_credentials` with a signed JWT (`private_key_jwt`), a JWKS and `system/` scopes.
  That flow was not tried here.
- Useful side result: `POST /apis/default/fhir/Patient` with a `user/Patient.write` scope
  returned `201 Created` in 0.4 s. Whether `Observation` writes work is spike S1's question.
- The token request (1.3 s warm) is the slowest single call. Cache the token in the proxy for
  its lifetime rather than fetching one per Share.

**Proposed brief edit** (paragraph under the Components table). Replace "Add a 2 GB swap file and
a low-memory MariaDB config; if page loads are unacceptable, move to e2-small, which leaves the
free tier." with:

> Add a 2 GB swap file, cap Apache at four worker processes and keep a low-memory MariaDB config.
> Spike S2 measured 216 to 330 MB of RAM still available at idle and no out-of-memory kills. The
> real limit is the shared CPU: after about 20 seconds of sustained load, responses slow roughly
> eightfold until the VM rests, and first boot takes about 15 minutes. That is acceptable for one
> reviewer at a time. If it is not, move to e2-small, which leaves the free tier.

The open-question entries "OpenEMR on the e2-micro" and (for the memory half only) "mllp-adapter
on e2-micro" can be ticked.

## Not verified

- **e2-small was not tested**, because the e2-micro did not fail. Its price was not looked up
  from a live source in this spike. From memory the list price in `us-central1` is roughly
  $12 per month for the VM, against roughly $6 for an e2-micro outside the free tier; check the
  pricing page before relying on either figure. An e2-small has the same two shared vCPUs with a
  larger burst allowance, so it would ease the CPU caveat but not remove it.
- **Real browser use.** Only single URLs were timed with `curl`. A logged-in OpenEMR session loads
  many scripts and frames per page; that was not measured, and neither was anything from outside
  the VM.
- **The cause of the slowdown.** CPU burst limiting is inferred from behaviour (same test, six
  times slower when repeated). The VM's CPU metrics in Cloud Monitoring were not inspected.
- **The cause of the 5-minute first boot** (slow disk is the suspicion).
- **Long-run stability.** The longest single uptime was about 30 minutes. Memory growth over
  days, log growth and OpenEMR's background jobs were not observed.
- **The MLLP adapter under traffic.** It was idle with a placeholder store. Its memory while
  forwarding messages is not known (S4).
- **`vm.swappiness`** values other than the default 60.
- **Each tuning in isolation.** Stock and tuned were compared as whole sets, and the stock burst
  run started with a partly used CPU allowance, so its latency figures are not a fair comparison.
  Its process count and swap figures are.
- **`OPENEMR_SETTING_*` variables** were not tried on the production image; the source suggested
  they are not handled there, and the spike went straight to SQL.
- **OpenEMR memory with real data** or with the patient portal and other modules in use.
- **`gcloud compute ssh`** was not attempted. Everything ran through the startup script and a
  small metadata-driven command runner writing to the serial console.
