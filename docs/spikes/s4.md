# Spike S4: Google's mllp-adapter on an e2-micro next to MariaDB

## Verdict

**Yes, with caveats: use Google's adapter on the e2-micro.** It ran next to a MariaDB container
in about 27 MiB of RAM, forwarded every correctly framed message to the HL7v2 store, and returned
the store's acknowledgment to the sender in a median of 75 ms. The Python fallback listener is
not needed.

The caveats, each explained below:

1. The published flag names differ from what older examples show; two wrong flags put the
   container in a crash loop on the first attempt.
2. The store is far more lenient than D7 assumes. Most "malformed" messages are accepted. Only a
   few shapes produce a negative acknowledgment, and badly framed input produces **no response at
   all**.
3. The identity test only proved that a project-level Editor can ingest. The least-privilege role
   was not exercised (see "What was not verified").
4. `latest` is a moving tag. Pin the image by digest.

Terms used in this note:

- **MLLP** (Minimal Lower Layer Protocol) is the thin TCP wrapper HL7v2 messages travel in: one
  start byte `0x0B`, the message, then two end bytes `0x1C 0x0D`.
- An **ACK** is the short HL7v2 reply message a receiver sends to say what it did with a message.
  A **NACK** is the informal name for an ACK that reports a failure.
- **MSA-1** is the first field of the ACK's `MSA` segment, and holds the acknowledgment code.
- **AA** (Application Accept) means the message was accepted. **AE** (Application Error) means
  the receiver found an error in the message. **AR** (Application Reject) means the receiver
  refused it for a reason other than its content (for example an unsupported message type).
- **MSA-2** echoes the sender's message control ID (MSH-10), so the sender can match the ACK to
  the message. **MSA-3** is a free-text error message.

## What was run

Everything ran from the instance startup script; results were read from the serial console.
SSH was not attempted.

### Adapter

The image has no entrypoint or default command, so the binary path must be given.

```bash
docker run -d --name mllp-adapter --restart unless-stopped \
  -p 127.0.0.1:2575:2575 \
  gcr.io/cloud-healthcare-containers/mllp-adapter@sha256:92eaa0fc5fcd0eb7ff62bd28c9140dcd7582bfec20790e5b203ca8dc75c4a90f \
  /usr/mllp_adapter/mllp_adapter \
  --port=2575 \
  --receiver_ip=0.0.0.0 \
  --hl7_v2_project_id=<project-id> \
  --hl7_v2_location_id=us-central1 \
  --hl7_v2_dataset_id=<dataset-id> \
  --hl7_v2_store_id=<store-id> \
  --log_error_msg=true
```

(The spike pulled `:latest`; the digest form above is what T21 should use.)

Flag notes, from the binary's own usage text:

- The store flag is `--hl7_v2_store_id`. The first attempt used `--hl7_v2_hl7_v2_store_id` and
  `--logtostderr`, both seen in older examples. Neither exists in this build: the adapter printed
  its usage, exited with status 2, and Docker restarted it in a loop.
- `--api_addr_prefix` is marked deprecated. Leaving it out works; the adapter picks the endpoint.
- `--receiver_ip=0.0.0.0` is the listen address inside the container. What is reachable from
  outside is decided by Docker's `-p`. The spike bound to `127.0.0.1` only.
- `--credentials` is optional; without it the adapter uses the VM's service account through the
  metadata server. No key file is needed on the VM.
- `--export_stats` defaults to `true` and sends metrics to Cloud Monitoring. It logged one
  `Failed to export to Stackdriver: ... Internal error` line during the run. A second adapter
  started with `--export_stats=false` worked normally.
- `--log_error_msg=true` logs the store's error text for each NACK. `--log_ack`,
  `--log_nacked_msg` and `--log_input_msg_in_base64` log message content, which is patient data
  in production; leave them off.
- `--mllp_addr`, `--pubsub_project_id` and `--pubsub_subscription` are for the outbound direction
  (store to an MLLP receiver). Not used.

### Startup script outline

```bash
# 2 GB swap
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# Docker
DEBIAN_FRONTEND=noninteractive apt-get update -qq && apt-get install -y -qq docker.io

# MariaDB, low-memory settings; root password generated on the VM, never printed
umask 077; head -c 24 /dev/urandom | base64 > /opt/s4/db-root-pw; umask 022
docker run -d --name mariadb --restart unless-stopped \
  -e MARIADB_ROOT_PASSWORD_FILE=/run/secrets/db-root-pw \
  -v /opt/s4/db-root-pw:/run/secrets/db-root-pw:ro -v mariadb-data:/var/lib/mysql \
  mariadb:11.4 --innodb-buffer-pool-size=64M --performance-schema=OFF \
  --max-connections=30 --key-buffer-size=8M --table-open-cache=200

# Project ID from the metadata server, so nothing is hardcoded
PROJECT=$(curl -sf -H Metadata-Flavor:Google \
  http://metadata.google.internal/computeMetadata/v1/project/project-id)
# ...then the adapter `docker run` shown above
```

From boot to both containers running took about 2 min 20 s (Docker install 40 s, image pulls the
rest).

### Test client

A 100-line Python script on the VM opened a TCP connection to `127.0.0.1:2575`, wrote the bytes,
and read until it saw `0x1C 0x0D`, the peer closed, or a timeout passed.

## Test messages (synthetic)

The valid message. Segments are separated by a carriage return (`\r`), shown here as line breaks.

```
MSH|^~\&|CUFFSIM|PULSEBRIDGE|PHR|PULSEBRIDGE|20261113205329||ORU^R01^ORU_R01|S4-205329-0001|P|2.5.1||||
PID|1||SYN-000123^^^PULSEBRIDGE^MR||TESTPATIENT^SYNTHIA||19800101|F
OBR|1||S4-ORD-1|85354-9^Blood pressure panel^LN|||20261113205329
OBX|1|NM|8480-6^Systolic blood pressure^LN||120|mm[Hg]^mm[Hg]^UCUM|||||F|||20261113205329
OBX|2|NM|8462-4^Diastolic blood pressure^LN||80|mm[Hg]^mm[Hg]^UCUM|||||F|||20261113205329
```

- `MSH` is the message header: separators, sending and receiving application and facility,
  timestamp, message type `ORU^R01` (an unsolicited observation result), control ID (MSH-10),
  processing ID `P`, version 2.5.1.
- `PID` identifies the patient: a made-up medical record number and name.
- `OBR` describes the observation request the results belong to: the LOINC blood pressure panel.
- `OBX` carries one result each: value type `NM` (numeric), LOINC code (OBX-3), value (OBX-5),
  UCUM unit (OBX-6), status `F` for final (OBX-11), observation time (OBX-14).

Malformed variants were made by editing this message; each is described in the results table.

## Results

### Valid message

Sent over MLLP, the message arrived in the store. `messages.list` with `view=FULL` returned it
with `messageType: ORU`, `sendFacility: PULSEBRIDGE`, `sendTime`, `patientIds: [{value:
SYN-000123, type: MR}]`, the raw bytes in `data` (base64), and `parsedData` with five segments.
(`gcloud healthcare hl7v2-messages` is not a command in the installed gcloud; REST was used.)

Raw ACK received by the sender:

```
\x0bMSH|^~\&|PHR|PULSEBRIDGE|CUFFSIM|PULSEBRIDGE|20261113205330||ACK|6c52ee99-ac83-49c0-b976-cd739886d858|P|2.5.1\rMSA|AA|S4-205329-0001\x1c\r
```

The ACK swaps sender and receiver, uses a fresh UUID as its own control ID, repeats the version
from MSH-12, and has message type `ACK` (not `ACK^R01`). `MSA|AA|S4-205329-0001` is the accept
code plus the original control ID.

Raw NACK for an unparseable message (b1):

```
\x0bMSH|^~\&|||||20261113205348||ACK|63a5f7b7-0ae4-42a6-b517-eed75c1861a3\rMSA|AE||Invalid MSH header\x1c\r
```

Raw NACK for line-feed terminators (a6):

```
\x0bMSH|^~\&|||||20261113205348||ACK|57eb795c-d742-4a29-8bdc-4a8ed3c7f356\rMSA|AE||invalid segment terminator, store expects: "\E\r"\x1c\r
```

(`\E\` is HL7's escape sequence for a backslash, so the text reads `"\r"`.)

What this means:

- Every NACK seen was **AE**. **AR was never returned.**
- A NACK for an unparseable message has empty sender and receiver fields and an empty MSA-2,
  because the store could not read the original header. The sender can only match it to its
  message by connection, not by control ID.
- The store does not validate message content. It checks that the header and segment structure
  can be split, nothing more. Missing fields, wrong data types, unknown codes and unknown
  versions all get AA.
- The adapter does not log or answer bad framing. It waits for the end bytes indefinitely, and
  nothing appears in its log when the client gives up.
- When the Healthcare API call itself fails (404 here; a permission error would take the same
  path), the adapter logs `MLLP Receiver: failed to handle message: googleapi: Error 404 ...` and
  drops the connection without sending an ACK.
- After all malformed cases, a valid message on a new connection was accepted normally. The
  adapter did not restart (`RestartCount` 0, not OOM-killed).
- Versions 2.3, 2.3.1, 2.4, 2.5, 2.5.1, 2.6, 2.7 and 2.8 were all accepted with AA. 2.5.1 is fine.
- MSH-15 and MSH-16 (the enhanced-mode acknowledgment switches) are ignored: `AL`/`AL` and
  `NE`/`NE` both produced the same immediate AA.

### Store settings

| Setting | Value tested | Effect |
| --- | --- | --- |
| `rejectDuplicateMessage` | unset (default) | The same bytes sent twice: AA both times, **one** message stored. Ingest is idempotent. |
| `rejectDuplicateMessage` | `true` | Second send returns `MSA\|AE\|<control-id>\|message already exists`. |
| `parserConfig.allowNullHeader` | unset (default) | A message with no MSH is rejected: AE, `Invalid MSH header`. |
| `parserConfig.allowNullHeader` | `true` | A message starting with `PID`, and the bare string `MSH`, are accepted with `MSA\|AA` and stored. Free-text garbage is still AE (`Invalid segment name "THI"`). |
| `parserConfig.version` | attempted to change to `V3` | Refused: `'parser_config.version' field is immutable after HL7v2 store creation`. Not tested further. |
| `parserConfig.segmentTerminator` | unset (default) | Segments must end in `\r`; `\n` is AE. Not changed. |

The store's `parsedData` numbers MSH fields one lower than HL7 does (message type is under
`8.1`, HL7 calls it MSH-9.1), because HL7 counts the field separator itself as MSH-1. This does
not affect us: `v2-to-fhir` parses the raw `data` with `hl7apy`.

## IAM and scopes

- The VM ran as the Compute Engine default service account with the `cloud-platform` scope.
- Ingest worked with **no IAM change**. The store's IAM policy stayed empty; no store-level
  binding was added.
- The reason is that this project grants the default service account `roles/editor` at project
  level, which already includes the ingest permission. That is the default for older projects
  and is far broader than the adapter needs.
- The adapter needs no key file. It gets tokens from the metadata server.

For T21 and the identity module: create a dedicated service account for the VM and grant it
`roles/healthcare.hl7V2Ingest` on the HL7v2 store only. This spike did not test that role on its
own, so the first apply of T21 should confirm a message is accepted. If `--export_stats` is left
on, the account would also need permission to write metrics; turning it off avoids that.

## Design consequences

### T13, cuff simulator

- Frame with `0x0B` ... `0x1C 0x0D` and end every segment with `\r`. `hl7apy`'s ER7 output
  already uses `\r`; do not convert to `\n` anywhere on the way.
- Set a read timeout (a few seconds is ample against a 111 ms worst case) and treat three
  outcomes as distinct: an ACK frame, connection closed with no data, and timeout. The last two
  have no ACK to show; the trace panel needs a "no acknowledgment received" state with the reason.
- Read MSA-1, MSA-2 and MSA-3. Show MSA-3 as the reason on a NACK. Do not require MSA-2 to match
  on a NACK, because it is empty when the header could not be read.
- Accept `ACK` as the reply message type; it is not `ACK^R01`.
- The "send malformed" samples (T07) that reliably show a NACK are: no MSH segment (AE, `Invalid
  MSH header`) and line-feed segment terminators (AE, `invalid segment terminator`). A missing
  end byte demonstrates the timeout path. Missing OBX-14, non-numeric OBX-5 and an unknown code
  get AA and belong to the mapper's class.
- Resending identical bytes is safe with the default store setting: AA, no second copy.

### T21, edge-vm module

- Pin the adapter by digest, pass the binary path as the command, and use the flag names above.
- Take the project ID from the metadata server or a Terraform variable in the startup script.
- Publish the port on the VM's interface (`-p 2575:2575`) for the Cloud Run simulator; the spike
  only tested loopback. The firewall rule from the brief still applies.
- Use `--restart unless-stopped`. A wrong flag makes the container crash-loop silently, so the
  startup script should check the container is `Up` after a few seconds and log if not.
- Set `--export_stats=false` unless metrics are wanted, and keep the content-logging flags off.
- The adapter's footprint (about 27 MiB) is not a factor in the 1 GB budget. OpenEMR is; that is
  S2's question.
- Healthcare module: leave `rejectDuplicateMessage` and `allowNullHeader` at their defaults, and
  decide `parserConfig.version` before the first apply, because changing it later means replacing
  the store.

### D7, malformed message handling

The three-layer model holds, but the middle layer catches less than the table says, and there is
a fourth outcome with no ACK at all. Proposed replacement rows for the table in
`docs/workplan.md`:

| Class | Example | Caught by | What the user sees |
| --- | --- | --- | --- |
| Unparseable | no MSH segment, wrong segment terminator, separators that disagree with MSH-1, empty payload | HL7v2 store at ingest; the adapter relays the store's reply | Commit-level `AE` with the store's reason from MSA-3 |
| No acknowledgment | bad MLLP framing (adapter waits silently); Healthcare API error such as a missing store or denied permission (adapter closes the connection) | MLLP adapter | "No acknowledgment received" with timeout or connection closed |
| Parses but cannot be mapped | unknown OBX-3 code, missing OBX-14, non-numeric OBX-5, empty or unknown MSH-9 or MSH-12, MSH-only message | `v2-to-fhir` mapping | Commit-level `AA`, application-level outcome `error` with a reason |

Two further points for D7:

- The store never returns `AR`, and it ignores MSH-15/16. Calling its reply the "commit-level
  acknowledgment" is our labelling; the store itself always replies in the original (simple)
  acknowledgment style with `AA` or `AE`.
- The mapper must expect stored messages that are barely HL7: a header with no message type, or
  a lone `MSH|^~\&`. These arrive with commit-level AA and must end as application-level `error`,
  not a crash.

### Proposed brief edits

- "Open questions and spikes": tick "mllp-adapter on e2-micro" and drop the Python listener
  fallback.
- MVP checklist line on malformed messages: change "the store or adapter rejects unparseable
  messages and the simulator shows the NACK" to say that the store rejects unparseable messages
  with `AE`, and that bad framing or an API failure yields no ACK, which the simulator shows as a
  timeout or closed connection.
- Components table, MLLP adapter row: no change.

### Question 5, the Python fallback

Not needed. For the record, it would have to: listen on TCP and handle connections
concurrently; buffer bytes and extract frames between `0x0B` and `0x1C 0x0D`, including several
frames per connection; get a token from the metadata server and refresh it; POST each payload,
base64-encoded, to `messages:ingest`; write the base64-decoded `hl7Ack` from the response back
inside an MLLP frame; and pass through the NACK the API returns with a 400 response. It would
also need a decision the Google adapter does not make: what to send the caller on a framing
timeout or an API failure.

## What was not verified

- **Least-privilege identity.** Ingest was only proven with project-level `roles/editor`.
  `roles/healthcare.hl7V2Ingest` alone on the store, a dedicated service account, and any scope
  narrower than `cloud-platform` were not tested.
- **Network path from Cloud Run.** All messages came from inside the VM over loopback. Latency
  from the simulator, the firewall rule and the published port on the external interface are
  untested.
- **Memory with OpenEMR present.** MariaDB was idle with an empty database and OpenEMR was not
  running. Combined memory pressure is S2.
- **Long-running behaviour.** The VM was up for about 12 minutes and handled about 60 messages.
  Memory growth over days, token refresh after an hour, and behaviour across a VM reboot were not
  observed.
- **Pub/Sub.** Out of scope (S5). In particular, whether a duplicate that is accepted but not
  stored a second time publishes another notification is unknown.
- **Parser versions V2 and V3, custom schemas and `segmentTerminator`.** Only the default parser
  was used; the version cannot be changed on an existing store.
- **Stats export.** The single Cloud Monitoring export error was not investigated.
- **Concurrency and large messages.** Messages were sent one at a time and were about 420 bytes.
- **`gcloud compute ssh`.** Not attempted.
- **Non-UTF-8 input** and the `--fallback_encoding` flag.
